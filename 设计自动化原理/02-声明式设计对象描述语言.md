# 第二章　声明式设计对象描述语言

## 2.1 描述语言是设计系统的入口

设计自动化需要一种机器可读、人员可审查、工具可交换的设计对象表示。它既可以采用专用领域语言，也可以采用带严格模式约束的通用数据格式。关键不在语法形式，而在于它能否成为设计意图和系统语义的稳定入口。

声明式语言主要描述“希望什么成立”：系统由什么组成，接口如何连接，参数受到什么约束，需要满足什么目标，以及哪些结果必须被生成。它不必规定每一次求解和编辑的具体步骤。

声明式并不排斥命令式计算。生成器、仿真器和优化器内部仍可执行复杂算法；声明式描述负责为这些算法提供明确契约，并把它们的输出重新纳入统一模型。

## 2.2 设计对象的七个语义层

一种可用于设计自动化的描述，通常需要覆盖以下层次。

### 身份层

每个系统、部件、接口和设计决策都应具有稳定身份。显示名称可以变化，身份不应随一次重新生成而任意改变，否则差异比较、评价缓存和问题追溯都会失效。

### 组成层

描述系统层次、部件类型、实例数量、可选组件和从属关系。组成层回答“系统由什么构成”。

### 参数层

描述参数名称、类型、单位、取值范围、默认值、来源和是否允许自动修改。单位与维度应是语言的一部分，而不能只存在于命名约定中。

### 接口层

描述端口、连接类型、方向、容量、兼容条件和外部契约。接口使部件可以独立演化，也使选型与拓扑检查可以自动执行。

### 行为层

描述功能、状态、输入输出关系以及必要的性能模型。并非所有部件都需要完整动态模型，但自动评价需要知道应该调用何种行为近似。

### 空间层

描述几何包络、位置、姿态、安装空间、操作空间、维护空间及禁入区域。用于碰撞检查的几何和用于采购交付的精细几何可以是不同表示，但应保持关联。

### 依据与溯源层

描述对象由哪项需求驱动、由哪个数据源产生、经过何种标定，以及当前仍存在哪些假设和未知量。

## 2.3 一个抽象示例

下面的示例不绑定具体行业，只展示声明式描述的结构：

```yaml
schema: design-object/v1
system: example-system
basis: project-basis@v3
ruleset: project-rules@v2

components:
  - id: unit-a
    type: library/unit@2.4.1
    parameters:
      capacity: 120
      layout_mode: fixed
    interfaces:
      input: port-a-in
      output: port-a-out

connections:
  - id: link-01
    from: unit-a.output
    to: external.consumer
    constraints:
      - capacity_sufficient
      - compatible_protocol

deliverables:
  - system-model
  - evaluation-report
  - component-schedule
```

真正重要的不是 YAML 语法，而是：模式、依据、规则、部件版本、稳定身份、参数、接口、连接和交付要求都被显式表达。

## 2.4 已知、未知与待定

设计早期不可能拥有全部信息。描述语言应区分：

- **已知且已确认**：具有可靠来源；
- **已知但尚未确认**：存在临时值或假设；
- **待定但允许求解**：具有变量身份和允许范围；
- **缺失且阻塞评价**：必须补充后才能运行；
- **不适用**：经过明确判断，而非简单留空。

如果所有空值都被当作零或默认值，自动化会用确定的外表掩盖信息缺口。更稳妥的做法是让评估器声明自己需要哪些字段，并在输入不足时返回“无法判断”。

## 2.5 不变量与局部有效性

描述语言应允许定义跨字段、跨对象和跨阶段的不变量。例如：

- 每个输出接口必须有且只有一个有效连接；
- 实例参数必须处于所选类型的允许范围内；
- 被占用的维护空间不得与其他对象重叠；
- 已批准的设计意图不得在深化阶段被静默修改。

这些不变量既可以在编辑时即时检查，也可以作为生成算子的约束，使机器尽量少产生无意义候选。

## 2.6 模式演化与兼容性

描述语言本身也会演化。模式升级需要区分：

- 仅增加可选字段；
- 改变默认值或语义；
- 重命名或删除字段；
- 改变身份生成方式；
- 改变单位、坐标系或接口约定。

并非所有变化都能通过版本号自动说明影响。平台应提供迁移工具、弃用周期和兼容性测试，并把语言模式版本写入设计运行记录。

## 2.7 人机共同编辑

声明式描述并不意味着所有使用者都必须直接编辑文本。图形编辑器、表格、专业界面和自动化程序都可以修改同一份模型，但必须遵守共同的身份、约束和版本规则。

文本化带来的重要能力是差异比较和审查；图形化带来的重要能力是空间理解和专业交互。二者不应互相替代，而应共享语义模型。

## 2.8 描述语言的评价标准

一种描述语言是否适合作为设计自动化基础，可以用以下问题检验：

1. 它能否表达设计意图，而不仅是最终形状？
2. 它能否区分固定决策与开放自由度？
3. 它能否表达未知、假设和来源？
4. 它能否支持稳定身份、依赖分析和增量更新？
5. 它能否让不同评估器获得明确、足够的输入？
6. 它能否被审查、迁移、版本化和长期保存？

如果这些问题没有答案，再丰富的语法也可能只是另一种需要人工解释的数据容器。
