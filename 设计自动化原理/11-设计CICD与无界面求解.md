# 第十一章　设计 CI／CD 与无界面求解

## 11.1 持续集成的对象是可验证变更

面向设计的持续集成，是在每次设计变更后自动重建必要证据。它把描述语言、依赖、规则、求解器和交付物连接成可重复执行的流程。

一次典型运行可以包括：

```text
解析声明式描述
  → 校验模式与依赖
  → 还原锁定环境
  → 运行静态和规则检查
  → 执行快速评价
  → 调度高成本求解
  → 比较设计基线
  → 生成深化交付物
  → 发布评价报告和设计候选版本
```

并非每次变更都要执行全部步骤。流水线可以依据变更范围、项目阶段和风险等级选择评价深度，但发布前必须满足完整证据要求。

## 11.2 设计变更的审查

设计审查不应只比较文本差异。平台还应提供语义差异：

- 哪些部件、参数和接口发生变化；
- 哪些规则结果发生变化；
- 哪些性能指标改善或恶化；
- 是否新增豁免或开放问题；
- 哪些交付物被重新生成；
- 哪些变化来自依赖升级而非设计编辑。

语义差异使审查者能够把注意力放在后果上，而不是从大量格式变化中寻找实质修改。

## 11.3 持续交付不等于自动实施

在软件领域，持续交付或持续部署可以连接到运行系统。在物理工程领域，自动把设计发布到现场往往既不安全，也不具备授权基础。

本书采用更通用的定义：

> 设计持续交付，是持续产生经过规定验证、具有完整证据、可以进入批准和使用流程的设计版本。

交付物可能是受控模型、图纸、清单、计算书、配置包或软件发布候选。是否实施到真实世界，应由相应专业和授权流程决定。

## 11.4 无界面求解器作为 CI 任务

无界面求解器是从个人桌面工具走向平台能力的关键。作为 CI 任务，它应满足：

- 输入完整、显式且可机器读取；
- 不依赖人工点击或个人本机状态；
- 在版本固定、资源受限的环境中运行；
- 输出结构化结果、诊断和运行状态；
- 支持超时、取消、失败重试和资源限制；
- 保存日志、输入摘要和版本信息；
- 在适用时支持并行、缓存和增量运行。

无界面并不意味着去掉专业交互，而是把可重复的计算核心与交互式问题定义、结果审查分离。

## 11.5 任务契约示例

```yaml
job: system-performance-evaluation
inputs:
  design: locked-design@current-change
  basis: project-basis@v3
  ruleset: project-rules@v2
runtime:
  solver: domain-solver@7.1.0
  timeout: 45m
  resources: standard-compute-profile
outputs:
  - structured-result
  - diagnostics
  - evidence-manifest
policy:
  cache: content-addressed
  retry: transient-failures-only
  on_invalid_input: fail
```

契约的重点是输入、环境、输出和失败策略都可被平台理解，而不是把一次人工操作录制成不可维护的脚本。

## 11.6 评价成本与调度

CI 任务可以按反馈目标分层：

- 编辑时运行即时模式与局部约束检查；
- 提交变更时运行标准规则与快速评价；
- 合并前运行受影响的专业验证；
- 夜间或按需运行高成本仿真和大规模综合；
- 发布前运行完整验证与交付物一致性检查。

调度应优化“获得可信证据的时间”，而不只是服务器利用率。一个消耗大量计算却长期不反馈关键错误的流程，仍然不是高效流程。

## 11.7 缓存与可复现性

内容寻址缓存可以避免重复计算，但缓存键必须覆盖所有影响结果的输入。对于存在数值并行、随机搜索或外部服务调用的任务，还应明确结果可复现的条件。

如果无法逐位复现，系统至少应追求结论层面的可复现：在声明容差内，关键状态和决策一致。超出容差的波动需要被报告，而不是随机选择一次结果作为真相。

## 11.8 证据清单

每次重要运行都应生成证据清单，记录：

- 设计变更与依赖锁定版本；
- 实际执行的评估器及其结果；
- 被跳过、缓存或增量复用的项目；
- 失败、无法判断和豁免状态；
- 生成的交付物及摘要；
- 人工审批和后续开放项。

证据清单把“流水线显示绿色”转化为可审查的具体含义。
