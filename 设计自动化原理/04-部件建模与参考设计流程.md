# 第四章　部件建模与参考设计流程

## 4.1 一种可执行的总体结构

本章给出一个通用参考流程：

```text
资产准备                    项目输入
0 部件建模          设计依据＋现状模型＋项目规则配置
      \                    /
       1 选型
         ↓
       2 实例化
         ↓
       3 空间布置
         ↓
       4 拓扑连接
         ↓
       5 系统级综合评价
         ↓
       6 自动深化与交付
         ↓
       7 发布、实施反馈与再标定
```

0 是可复用资产准备，1—4 是项目设计的主要承诺层级。这个顺序不是严格瀑布：空间与拓扑会相互影响，综合评价也可能要求回退到任何前序阶段。

流程的价值在于，每一步只增加一类主要承诺，并在该层建立检查与回退机制。

## 4.2 第零步：部件建模

部件模型是可计算、可验证和可复用的设计资产，而不只是三维几何。一个完整部件包通常包含：

- 类型身份和版本；
- 参数、单位、默认值与允许范围；
- 功能和性能模型；
- 几何包络与空间需求；
- 输入输出接口及兼容条件；
- 可连接对象和连接约束；
- 成本、供应和生命周期属性；
- 适用的规则与评估器；
- 测试样例、验证状态和适用边界。

并非每个部件都必须具备全部属性，但缺少某项属性会限制自动化能力。例如，没有维护包络的部件仍可参与几何布置，却不能自动证明维护可行。

部件包发布前，应像软件包一样经过测试：参数范围是否有效，接口是否自洽，性能模型是否在声明范围内工作，几何与数据是否一致。

## 4.3 第一步：选型

选型回答“使用哪一类或哪一档部件”，主要依据功能、容量、环境、接口、标准和供应条件筛选候选。

选型阶段不宜过早收敛到唯一产品。更稳健的输出是候选集合，以及每个候选的：

- 可满足需求；
- 可调参数范围；
- 已知限制；
- 与其他候选的关键差异；
- 被淘汰候选及淘汰原因。

如果没有任何候选可行，系统应区分四种原因：需求相互冲突、规则配置过严、部件库覆盖不足、评价模型或数据错误。它们对应完全不同的处置，不能一律通过放松约束解决。

## 4.4 第二步：实例化

实例化把部件类型变成项目中的具体对象，回答“创建哪些实例、数量多少、各自参数是什么”。

主要工作包括：

- 分配稳定身份；
- 绑定具体参数；
- 确定实例数量；
- 解析部件依赖；
- 固定部件包版本；
- 建立实例与设计依据的追溯；
- 检查参数组合和实例级约束。

选型与实例化之间可以迭代。例如，某种类型功能上适用，但在所需数量和参数组合下无法满足约束，就需要重新选型。

本阶段输出项目系统组成模型，而不是最终施工图或制造模型。

## 4.5 第三步：空间布置

空间布置确定实例的位置、姿态和空间关系。它至少应考虑：

- 安装空间与结构边界；
- 操作、维护和安全空间；
- 碰撞、净空和间距；
- 朝向、可达性和外部接口；
- 施工、装配或更换顺序；
- 为连接和路由预留的空间。

布置结果不仅是坐标，还应包括使用的空间模型版本、碰撞检查结果和未解决的空间冲突。

空间不可行时，可以优先调整实例数量、规格和参数，再决定是否回退选型。这样可以避免把局部空间问题误判为系统原理问题。

## 4.6 第四步：拓扑连接

拓扑连接定义系统如何共同工作，包括：

- 端口与接口匹配；
- 连接关系和网络结构；
- 方向、层级和所有权；
- 容量与负载分配；
- 冗余、隔离和故障路径；
- 连接所需的中转部件；
- 路由及其空间可行性；
- 连通性、完整性和可达性。

拓扑与空间布置之间存在双向约束：布置为连接提供路径，连接又可能要求调整位置、朝向和间距。因此，自动化流程通常需要在二者之间执行局部迭代，而不是只运行一次。

## 4.7 系统级综合评价

完成 1—4 只意味着系统描述基本完整，并不意味着设计成立。还需要执行：

1. 完整性、身份和依赖检查；
2. 项目规则与豁免检查；
3. 接口和约束满足检查；
4. 性能、容量和专业计算；
5. 必要的仿真与测试；
6. 施工、维护和全生命周期评价；
7. 鲁棒性与不确定性分析；
8. 多目标比较和人工决策。

评价的具体组织方式见第五章。这里需要强调的是，评价结果应能映射回承诺层级。

## 4.8 回退策略

| 失败表现                       | 优先回退位置               |
| ------------------------------ | -------------------------- |
| 单个参数越界或组合不当         | 实例化                     |
| 局部碰撞、维护空间不足         | 空间布置                   |
| 路由不通、局部连接冲突         | 空间布置或拓扑连接         |
| 容量不足、关键接口不兼容       | 选型                       |
| 需求之间不存在共同可行解       | 设计依据                   |
| 所有库内候选均不满足合理需求   | 部件库扩展                 |
| 指标合格但存在不可接受价值权衡 | 人工决策，而非继续自动加权 |

回退的目标不是让系统盲目重新开始，而是以尽可能小的设计变更消除失败原因。

## 4.9 阶段门与证据

每个阶段都可以设置轻量阶段门：

- 选型门：是否存在合理候选，淘汰理由是否清楚；
- 实例化门：组成、参数和依赖是否完整；
- 布置门：空间硬约束是否满足；
- 拓扑门：系统是否连通、兼容且容量可行；
- 发布门：系统级证据是否充分，开放项是否获授权接受。

阶段门不应意味着前一阶段永远不可修改，而应意味着后续工作知道当前基于什么版本、什么假设和什么证据展开。
