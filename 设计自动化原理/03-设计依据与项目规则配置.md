# 第三章　设计依据与项目规则配置

## 3.1 设计依据不是项目说明文档的简单集合

设计依据是全部设计判断的输入契约。它可以来源于需求文件、标准规范、现场勘察、合同条件、用户决策和既有系统数据，但进入自动化流程后，不能只保留为难以定位的自然语言附件。

一份可计算的设计依据，应尽量说明：要求是什么，来源在哪里，由谁确认，适用于哪些对象，何时生效，如何验证，以及发生冲突时由谁处理。

它通常包括：

- 功能需求、设计容量和性能目标；
- 场地、环境、边界和外部接口条件；
- 适用标准及其版本；
- 成本、工期、供应和运维约束；
- 必须保留的既有系统与已批准决策；
- 假设、待定项和不确定性；
- 验收标准、审批权限与责任边界。

## 3.2 从自然语言要求到可验证契约

并非每条设计要求都能直接形式化，但每条关键要求都应至少拥有一个验证处置：

| 要求类型               | 可能的验证方式                     |
| ---------------------- | ---------------------------------- |
| 数值容量要求           | 参数检查、解析计算、仿真           |
| 接口兼容要求           | 类型检查、连接规则检查             |
| 空间与安全要求         | 几何检查、专业规则评估器           |
| 主观体验要求           | 人工评审、用户测试、偏好记录       |
| 合同或管理要求         | 文档检查、审批记录                 |
| 尚无可靠评价方法的要求 | 标记为开放问题，指定责任和后续计划 |

自动化不应把所有要求强行转换为数值指标。对暂时无法计算的要求，显式保留人工验证，比制造一个看似客观的代理指标更诚实。

## 3.3 规则基线与项目配置

项目规则宜采用分层继承：

```text
通用规则 → 专业规则 → 组织标准 → 项目规则配置
```

项目层允许三种典型操作：

- **覆盖**：替换默认参数、适用范围或检查实现；
- **加严**：在通用要求之上提高项目要求；
- **豁免**：在明确范围内接受某项不符合，并记录批准与补偿措施。

“覆盖”具有最高灵活性，也最容易造成意外。因此，平台应显示最终合并结果及其来源，避免使用者只看到自己修改的局部配置，却看不到实际生效的规则全集。

## 3.4 豁免不是关闭检查

豁免是一项设计决策，而不是一个布尔开关。完整的豁免记录至少应包含：

- 被豁免的规则及版本；
- 适用对象和空间范围；
- 不符合的事实与评价证据；
- 豁免理由；
- 风险分析与补偿措施；
- 批准人和批准时间；
- 有效期、复审条件或关联项目阶段。

检查仍应运行并报告原始不符合，只是在最终处置中标记为“已豁免”。这样，后续项目能够发现曾经的风险接受，规则维护者也能分析哪些规则频繁需要豁免。

## 3.5 检查结果的状态语义

建议至少区分以下状态：

- **通过**：评估器在适用范围内完成检查，未发现不符合；
- **不通过**：存在明确不符合；
- **已豁免**：不符合仍然存在，但已按授权流程接受；
- **不适用**：经过适用性判断，该规则不作用于当前对象；
- **无法判断**：输入不足、模型不支持或结论不确定；
- **执行失败**：评估器未能正常完成运行。

“无法判断”和“执行失败”绝不能被汇总为通过。一个缺少输入的检查和一个已经完成的检查，具有完全不同的证据意义。

## 3.6 项目配置示例

```yaml
ruleset:
  base: organization/industrial-rules@4.2
  project: project-alpha/rules@1.3

overrides:
  - rule: clearance.minimum
    value: project-specific-value
    reason: confirmed-project-interface

tightenings:
  - rule: reliability.minimum
    level: enhanced

waivers:
  - rule: access.preferred-layout
    scope: [existing-unit-07]
    reason: brownfield-space-limitation
    compensating_checks:
      - maintenance-simulation
      - manual-operations-review
    approval: approval-record-2026-017
```

示例中的具体数值并不重要。重要的是覆盖、加严和豁免拥有不同语义，并能追溯到相应依据和批准。

## 3.7 需求、对象与证据的追溯

每项关键设计依据都应能连接到：

1. 受影响的设计对象；
2. 控制该对象的设计决策；
3. 执行验证的规则或评估器；
4. 产生的评价结果；
5. 最终审批或开放问题。

这条链可以双向使用。正向追踪帮助检查一项需求是否真正落实；反向追踪帮助解释一个部件或参数为什么存在。需求变更时，依赖图还能帮助确定需要重新评价的范围。

## 3.8 冲突与变更

设计依据内部可能出现冲突，例如容量目标、既有空间和投资上限无法同时满足。系统应把这种状态表达为“依据冲突”或“当前约束不可行”，而不是自行选择某一项忽略。

依据变更则应成为显式事件：记录变更内容、来源、批准和影响范围，并触发必要的增量评价。自动化系统可以帮助分析影响，却不应静默修改项目目标来换取可行解。

## 3.9 设计依据的发布

项目在某个阶段形成基线时，应同时冻结或锁定：

- 设计依据版本；
- 生效规则配置；
- 现状模型与标定数据版本；
- 关键假设和开放问题；
- 验证计划与审批权限。

此后每次变更都可以与基线比较。设计自动化由此从一次性计算，转变为能够管理演化的证据过程。
