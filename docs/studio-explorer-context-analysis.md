# 文件资源管理器层级与右键设计对照

- 日期：2026-11-12
- 状态：上下文菜单分析与实施建议；面板、工作区分区与项目根层级由 [DDR-0015](ddr/0015-studio-explorer-workspace-section-and-project-root.md) 修正，标题视图菜单与活动栏菜单由 [DDR-0016](ddr/0016-studio-explorer-and-activity-context-menus.md) 定义。下文记录当时观察与其他尚待实施的建议。
- 初次对照基线：`f79b4c2`，该轮开始时工作区干净
- 方式：既有 Google Chrome 中的 VS Code Web 与唯一 Tex Studio `8710` 实例实测，辅以当前代码审阅

## 结论

资源管理器应先区分三个层级：「资源管理器」面板标题、独立的「工作区」可折叠分区标题、分区内的项目根树节点。新建文件、新建文件夹、刷新与全部折叠属于工作区分区标题行，项目根是普通树条目，不承载这四个工具按钮。原分析只区分了面板标题与根节点，漏掉工作区分区，因而未识别根节点兼任分区标题的结构错误。

各层级的操作职责明确后，再分别组织目录与文件上下文。初次审阅时 Tex Studio 将面板标题、目录与文件复用为同一份六项菜单，导致文件菜单以新建、刷新、全部折叠开头，却没有文件打开方式、侧边打开和路径操作。对标应先明确目标、选择集合与能力，再安排菜单分组；不以复制参考产品所有条目作为目标。

最初的上下文菜单对照只做分析，没有修改产品代码，没有执行重命名、删除、剪切粘贴或上传下载。重命名输入观察后均取消。后续结构修正只处理上述三个层级与折叠职责，不顺带实施完整右键菜单或文件剪贴板。参考页面的菜单可能受文件类型、已安装扩展、宿主文件系统和平台快捷键影响，不能把本次所有条目都归为任何 VS Code 环境必然提供的能力。

## Chrome 实际观察

文件类型对照覆盖普通 TOML 与 Markdown。其中两边都检查了同一个项目文件：`build/project-preview-poc/20261111-replay/project-a/README.md`。另外检查普通目录、工作区根、单根工作区空白区域、两文件多选、标题栏菜单及重命名。

| 上下文               | VS Code Web 实测                                                                               | Tex Studio 实测／代码现状                            |
| -------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 普通文件             | 侧边打开、打开方式；选择比较；时间线；剪切／复制；下载；路径复制；重命名／永久删除             | 新建文件／文件夹、刷新、全部折叠；重命名／删除       |

| 普通目录             | 新建、文件夹内查找；剪切／复制／粘贴；传输；路径；重命名／永久删除                             | 仍是六项菜单，非空目录的重命名／删除也显示可用       |

目录菜单还观察到“在图像预览中打开”，不据此推定其属于通用目录必需操作。上传下载与永久删除的呈现亦与当前 Web 文件系统能力有关。

### 层级与折叠补充核对

用户截图与后续 Chrome 核对补足了原分析遗漏的层级：资源管理器面板标题下，先是带四个工具按钮的「工作区」分区标题，再是使用实际项目名的根树条目。工作区收起后文件树和四按钮隐藏，展开恢复先前的树展开状态；项目根的展开与收起独立于分区。

参考 VS Code Web 在深层目录展开时，第一次「折叠文件夹」先折叠子目录并保留根展开，第二次才收起根。Tex Studio 不照搬这个分步行为，继续遵守用户已经明确的「全部折叠」契约：一次收起根并清空子目录展开状态，工作区分区不收起。单独收起根则保留子目录展开状态。新建或定位主动展开工作区分区和所需路径。

这次最小修正只处理三层结构、四按钮归属与折叠职责；后文完整右键、多选、文件剪贴板等仍是后续建议。Tex Studio 修改后的实际验收另记，不由参考界面观察推定通过。

### 选择、焦点与打开

VS Code Web 右键改变操作目标，但不顺带打开文件。例如右键 `texsys.toml` 时，中央仍为 README 文档。右键已选多项中的一项保留选择集合；右键集合外的一项改为该项。Escape 后焦点回到文件资源树。

Tex Studio 目前右键也只更新选择而不打开文档；Escape 后实测回到资源树条目。这部分行为应保留，不能因菜单内容不同而整体重写。后续需要显式表示右键目标、选择集合和键盘焦点，避免它们被一个 `selectedPath` 同时承担。

### 重命名与打开方式

VS Code Web 的“重命名...”进入树内原行输入，不弹路径窗口。对 `README.md` 默认选择范围为 0–6，即只选择 `README`，保留 `.md`；Escape 取消。Tex Studio 的“重命名…”仍弹“项目相对路径”窗口。

当前 macOS 参考菜单显示重命名快捷键为 Enter；Tex Studio 显示 F2。对标应依据操作系统设置快捷键，并让菜单与键盘进入同一操作，不应硬抄某个平台的标注。“...”本身并不代表模态窗口，参考产品的行内重命名同样有省略号。

VS Code Web 对普通 TOML 也显示“打开方式…”，打开后只有文本编辑器和设置默认编辑器入口。Studio 已由 DDR-0014 选择只在存在多种方式时显示选择器；建议 Explorer 同样避免单选项的无效入口，Markdown 等格式复用已有打开方式和默认值机制。

## 初次审阅识别的问题

1. [CoreWorkspace](../src/texsys/assets/studio/CoreWorkspace.tsx) 的 `explorerActions` 被文件行、目录行、根和标题栏更多共用，未表达上下文职责。
2. 非空目录的重命名／删除在前端可执行，但 [files.py](../src/texsys/studio/files.py) 明确拒绝。菜单能力与后端不一致。应实际实现所承诺的目录操作，或按真实条件禁用并解释，不能提交后才告知“不支持”。
3. 重命名仍使用路径模态窗口，缺少行内名称编辑；路径移动与名称修改也因此混在同一输入中。
4. 文件侧边打开、打开方式、复制路径等入口缺失，虽然 `openFile` 已支持指定编辑器组及呈现方式，可直接复用。
5. [ExplorerTree](../src/texsys/assets/studio/ExplorerTree.tsx) 没有多选和文件剪贴板能力。复制路径是文本剪贴板操作，文件复制／剪切／粘贴则需要完整文件操作契约，两者不能混称为“复制已实现”。
6. F2／Delete 路径没有复用菜单的 busy 判断，存在键盘和菜单可用性不一致的问题。此项来自代码审阅，未在运行中的文件写入期间触发测试。

现有菜单组件支持点位、分组、子菜单、禁用原因和键盘导航，不需要新造菜单框架。行内新建、文件组、通用预览和搜索过滤也已有基础，优先补充窄操作接口。

## 建议的对标范围

### 首先统一上下文与既有能力

- 文件菜单按打开与呈现、路径、重命名／删除分组；Markdown 等有真实渲染能力的文件增加预览。新建、全局刷新、全部折叠不放在每个文件的右键菜单中。
- 目录菜单按新建与目录内查找、路径、重命名／删除分组。创建目标是该目录；从所选文件使用工具栏新建时，目标仍是其父目录。
- 根与空白使用项目容器上下文，不提供删除项目根、重命名项目根。当前单项目范围不照搬多根工作区管理。
- 新建文件、新建文件夹、刷新、全部折叠属于独立的工作区分区标题行；项目根树节点不承载工具栏。资源管理器面板标题栏更多只管理资源管理器；若没有实际的视图管理项，就删除重复菜单入口，不用文件操作填充。
- 重命名改为树内输入，默认选中文件名主体；Enter 确认，Escape 取消，错误留在行内。新建保留已有树内交互。
- 菜单、键盘、工具栏通过同一命令及可用性判断执行。不适用的动作隐藏；适用但暂时不能执行的动作禁用并给出原因；尚未实现的能力不显示空入口。
- 复制绝对路径、复制项目相对路径属于基础文本操作，建议补齐。删除名称必须与实际能力一致：目前没有回收站，不能暗示可恢复删除。

### 随后补齐通用文件能力

多选、范围选择、剪切／复制／粘贴及目录移动属于基础文件开发体验，建议作为下一批真实能力实施，不能为了缩短菜单永久归为“不做”。需要一起处理同名冲突、目录与二进制、父子路径重复选择、操作中的失败、打开文档与未保存草稿的迁移。

目录内查找可对接已有搜索路径过滤。当前终端只支持项目／仓库工作目录，任意子目录终端需要扩展真实后端能力，不能直接添加一个无效菜单项。

### 可裁剪项与独立评估项

| 项目                               | 建议                                                                                |
| ---------------------------------- | ----------------------------------------------------------------------------------- |
| 时间线、语言服务文件引用           | 当前不补；已有 Git 差异和历史保留。没有可靠引用服务时不以全文字符串匹配冒充语义引用 |
| 上传／下载、系统文件管理器、云共享 | 当前本地项目闭环没有明确需要，暂不增加；未来按宿主或交付需求决定                    |
| 多根工作区管理、文件夹独立设置     | 不随本轮菜单对标扩展当前单项目范围                                                  |
| 图片目录预览等可选贡献             | 仅在确有对应能力与需要时提供，不照搬参考环境扩展菜单                                |
| 临时预览标签复用、锁定组           | 继续遵守 DDR-0014 的未纳入边界，不借 Explorer 对标重新引入                          |
| 两文件比较                         | 独立评估为普通文本差异能力；当前尚未承诺实现，不恢复磁盘采用流程                    |

“选择以进行比较”用于选择文件 A 后与文件 B 比较；它与 DDR-0014 删除的同一文件编辑缓冲区／磁盘比较、采用磁盘内容、更新保存基准不同。若实施，仅复用通用差异文档，明确两侧文件及内容来源，不增加工程变更接受界面。

当前另有一个待讨论的专业例外：模块目录名称单击打开模型，独立箭头才展开目录，这仍写在现行工作台契约中。建议最终让文件资源管理器的真实目录保持统一目录行为，模块查看通过部件库或显式操作进入；这属于后续需明确修订的设计建议，本轮未改动或撤销现有规则。

## 证据与下一步验收

本地证据在 `build/explorer-context-analysis/`：`observations.json` 保存各上下文的菜单、选择与活动标签观察，截图包括同一 Markdown 两边的菜单、TOML、目录、根、空白、多选、标题栏更多及行内／模态重命名。菜单出现不证明其每一项已执行，本轮没有对文件传输、删除或复制粘贴做功能验收。

实施时按“目标与选择 → 菜单职责 → 行内编辑与既有打开能力 → 多选和文件操作”顺序推进。验收至少覆盖文件、Markdown、空／非空目录、根、空白、多选；每项同时核对右键前后选中与打开状态、实际操作目标、取消与失败、键盘等价动作及草稿保留。该工作服务于工程输入与产物的普通文件工作流，不扩大物理效应覆盖，也不作为完整 POC 完成证明。
