## 背景

原理图等产物最初放在 Activity 的根对象文档内，缺少独立文件入口。改成文件后，又为工程产物额外增加标题、只读标签、目标判定、来源运行和缓存状态；普通 JSON 被包装为结果页面，而 Markdown 缺少预览。用户需要的是一致的文件工作流：特殊格式只替换预览实现，不能改变文件组件的布局和编辑方式。

## 决策

- 原理图、拓扑、BOM、场景与其他文件一样，从文件资源管理器或快速打开进入独立文档标签。文档按真实路径识别，同名不同路径必须能区分；切换 Activity 不改变已打开的文件。
- 所有文件共用文档标签、路径导航、工具栏、编辑区和保存行为。有预览实现时，在统一位置提供「预览 / 源代码」切换。不得使用「原始内容」代替「源代码」。
- 文件类型或专业扩展只提供预览内容的渲染实现。Markdown 渲染文档，图纸渲染图元，场景渲染几何；这些实现不额外增加文件标题、工程状态条、专用文档布局或新的 Activity。
- 普通 JSON 使用通用代码编辑器。构建清单、检查报告、BOM 数据不能因为具有工程含义就自动变成专用结果页面。图纸 JSON 若有图形预览实现，仍遵守同一个文件组件契约。
- Markdown 必须提供预览和源代码切换，表格、列表等内容应按文档格式显示。切换时保留同一文件身份及编辑内容。
- 普通文本文件可以编辑和保存，生成文件也不因产物身份被强制只读。预览读取当前文件或编辑缓冲区，不以历史构建快照代替当前内容。自动刷新不得覆盖未保存编辑，冲突沿用通用文件编辑行为。
- 文件预览不展示目标判定、运行 ID、缓存命中、历史适用性及「只读预览」等附加栏。这些构建信息继续保存在构建记录和日志中，不作为普通文件组件布局的一部分。
- 当前图形预览支持查看、选择、缩放和定位；源代码编辑只修改当前文件，不自动反向写回声明式设计。未来图形编辑仍应遵守同一文件组件与明确的源操作契约。

## 取舍与边界

统一文件组件让工程师可以使用已有的编辑习惯，专业扩展只负责格式表达。直接修改生成文件与修改设计源是两个不同的操作：重新构建可以覆盖生成文件的手工修改，但这不构成强制只读或增加专用确认流程的理由。运行快照和工具缓存仍属于内部存储，不作为日常编辑文件。

## 验收

在现有 Chrome 工作台中打开普通 JSON、Markdown、原理图和场景，确认文档框架和切换控件位置一致，专业内容只出现在预览区域。Markdown 表格能预览；普通检查 JSON 直接编辑；文件可以修改并保存，切换视图保留编辑内容。原理图、拓扑可同时打开且路径不混淆，切换 Activity 后仍可查看。文件预览中不存在构建状态、运行 ID、缓存或只读标签。外部重建、未保存编辑和读取乱序不得悄悄替换当前文档内容。
