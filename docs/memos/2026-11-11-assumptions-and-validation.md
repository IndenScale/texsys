# 工程验证与推进次序

日期：2026-11-11。分类：可入库。类型：实验与实现建议。

## 从一条完整体验开始

系统语义、物理反注、依赖管理、协作 CI 和 AI 操作可以沿着同一条体验逐步建设：设计变更产生影响，计算发现问题，工程师理解并修复，结果和审查材料同步更新。

本地依赖锁定、一次可靠检查和可复核的结果各自提供价值。以小系统贯通这些环节，再扩展领域和执行规模。

## 目标与观察指标

| 目标 | 实现机制 | 观察指标 |
| --- | --- | --- |
| 用系统语义组织检查 | 稳定身份、接口、单位、工况和行为表达 | 输入准备时间、规则表达量、问题定位效率 |
| 让物理实现反馈到行为 | 提取量映射到设计对象并触发重算 | 参数变化、响应变化、预测与参考结果的差异 |
| 发现组合变更的工程冲突 | 在联合基线上运行共同要求 | 检出、漏报、误报、未判定及原因 |
| 支持重跑和比较 | 保存输入、依赖、配置与结果 | 重建时间、数值差异、判据一致性 |
| 让 AI 承担机械操作 | 计划、批量执行、差异摘要和恢复 | 操作时间、复核时间、错误动作和修正次数 |
| 跨项目复用 | 共享对象、规则、设备包和适配器 | 第二个项目的新增代码与准备工时 |

## 最小工程闭环

从小型暖通系统开始，按以下步骤执行实验：

1. 固定要求、设计、工况、依赖和求解配置，取得参考结果。
2. 改变路由长度或局部阻力。
3. 将提取参数映射回同一设计对象，重新求解流量和压降。
4. 展示发生变化的要求、受影响对象及修复候选。
5. 修复设计，重跑计算并比较前后结果。
6. 由另一位审阅者使用留下的资料重跑并完成审查。

反注以提取值替换原理设计中的估算值，同时保存原预算。参考结果可以采用手算、独立实现或设备实测。

依赖升级、输入缺失和求解失败另设用例，分别检查结果更新、信息补齐提示和运行诊断。

## 组合变更实验

在一个已通过的基线中设置两项变更 A 和 B：一项消耗能力裕度，另一项增加系统需求。分别应用时满足要求，组合后越过限值。

| 运行 | 预期结果 | 观察内容 |
| --- | --- | --- |
| 基线 | 满足 | 初始需求与能力裕度 |
| 基线 + A | 满足 | A 消耗的裕度 |
| 基线 + B | 满足 | B 增加的需求 |
| 基线 + A + B | 不满足 | 组合影响及其来源 |
| 修复后的组合 | 满足 | 修复效果与其他断言的结果 |

先在暖通子系统之间建立这个案例，再沿专业接口扩展到多专业协作。

## 对照与指标

实验开始时记录基线、期望结果、容差和评价方法。对同一问题安排现有流程、相同结构化信息下的人工检查、新工具检查三个条件，比较信息整理与自动化分别带来的收益。

| 指标 | 记录方法 |
| --- | --- |
| 检出与漏报 | 对已知缺陷和正常案例逐项记录结论与原因 |
| 数据准备成本 | 从原始材料到第一次可运行输入的人工时间 |
| 复核成本 | 定位原因、阅读计算、确认修复的时间 |
| 执行成本 | 首次运行与重跑的耗时、资源消耗和缓存命中 |
| 重跑等价性 | 文本摘要、关键数值容差和判据结果 |
| 复用性 | 第二个相近案例新增的规则、适配代码与手工步骤 |
| AI 操作质量 | 人工与 AI 操作的用时、差异、撤销和复核过程 |

把资料整理、计算运行、误报处理、人工复核和规则维护合并计入总成本。

## 实现顺序

1. 跑通“设计变更—物理反注—计算—解释—修复”闭环。
2. 增加组合变更、依赖升级和异常输入用例。
3. 接入 AI 的计划、批量操作和差异解释。
4. 在第二个相近项目中复用对象、规则和工程包。
5. 扩展专业接口、定期回归与重仿真调度。
6. 建设 registry、第三方包分发和远程执行。
