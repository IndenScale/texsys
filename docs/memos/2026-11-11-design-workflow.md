# 备忘录：从需求到物理设计的验证闭环

- 日期：2026-11-11
- 分类：可入库

## 用户主张

用户提出的主线是：先确定指标，再确定架构与拓扑，完成原理设计，随后进行空间布局与布线。
完成物理设计后，提取实际布置带来的寄生影响，反注并验证原理设计是否仍满足要求。
这一过程可以逐步自动化，并以签核标准组织最终验证。
设计信息沿依赖关系逐渐明确，各项活动通过计算反馈持续迭代。

## 与现有七项专业活动对齐

专业流程采用[统一语言](../ul/glossary.md#专业设计流程)中的七项活动。
各活动可以按输入依赖并行开展；工程验证和跨专业协调贯穿设计过程。

| 专业活动          | 本备忘录关注的输入与输出                                 | 后续发现问题时的回路                     |
| ----------------- | -------------------------------------------------------- | ---------------------------------------- |
| 01 需求定义       | 确定规定工况下的总容量、可靠性、空间及其他要求和验收准则 | 记录需求变化的理由、依据和影响           |
| 02 架构设计       | 选择技术路线和拓扑，分配容量，定义接口及冗余配置         | 容量不足或故障路径不成立时重新分配与选型 |
| 03 原理设计       | 定义流向、运行模式、控制、联锁、切换和故障响应           | 新增容量或冗余需求反馈给架构设计         |
| 04 部件选型       | 将规格、性能和接口要求绑定到候选或确定型号               | 实际设备能力不满足时调整型号或上游设计   |
| 05 物理设计       | 确定设备位置、管线路由、净空及安装维护条件               | 提取影响行为的实际参数并重新验证         |
| 06 工程验证       | 汇集各阶段和 DfX 的证据，关联要求、工况与版本            | 未通过时回退到能解决问题的活动           |
| 07 跨专业设计协调 | 核对接口、采用版本、变化影响和未决事项                   | 上游变化触发有关专业复核                 |

稳态 0D 总容量由需求定义确定，容量分配由架构设计完成。
原理设计使用既定配置分析动态与故障行为，新发现的容量缺口反馈给架构设计。
设计发布是交付里程碑，汇集这些活动形成的模型、图纸和验证结果。

## 空间先验进入设计输入

既有建筑、设备运输路径、结构开洞、层高、场地边界和维护通道可能在原理设计前就已确定。
这些空间条件直接进入需求和架构输入。
概念布置也可以先行，用于检验技术路线是否有基本的空间可行性。

应同时保留两条演化轴：

- 逻辑信息：组成、连接、行为和工况逐渐明确。
- 空间信息：未放置、粗布置、局部确定、约束完整的布局逐渐明确。

两条轴通过参数和约束交换信息，分别展示当前状态与设计成果。
现有 [ADR-0018](../adr/0018-deliverable-semantics-and-baseline-gates.md) 已接受这种正交关系，以及“过程自由、基线有门”的原则。

## 反注的对象与证据

“寄生”在这里指理想化原理设计未完全体现、却会改变行为的物理实现因素。
各专业用适合自身物理过程的等效模型定义具体参数。

| 物理实现信息         | 可提取或更新的模型输入         | 模型条件                           |
| -------------------- | ------------------------------ | ---------------------------------- |
| 管路长度、弯头与高差 | 阻力、等效长度、静压条件       | 介质、流态、局部损失模型及几何精度 |
| 设备排列与周围空间   | 维护净空、可达性、散热边界     | 检修动作、观察位置及环境假设       |
| 线路长度与实际连接   | 专业定义的阻抗、压降或时延输入 | 线路模型、运行工况及计算适用范围   |
| 支承和安装位置       | 支承条件、附加荷载或连接约束   | 结构模型、材料参数及荷载组合       |

几何参数回注到模型及验证证据，再由模型重新生成图纸。
将“估算值”替换为“提取值”时，应保留原预算、来源、状态变化及受影响结论。

## 建议的闭环记录

每次反注建议形成以下最小记录：

1. 输入设计修订、依赖锁和适用工况。
2. 物理实现的来源版本，以及本次提取范围。
3. 参数的旧值、新值、单位、精度和状态。
4. 受影响的需求、接口、行为模型及验证项。
5. 所用评估器、执行配置、结论与无法判断项。
6. 设计者对调整、风险接受或继续深化的处置。

数据缺失、模型不适用、求解失败与工程不通过需要分别表达。
评估器计算结果，判据判断工程是否通过。
采用更精细模型时，保留旧结果用于比较，并生成新版本的验证结论。

## 从最小案例验证方法

选择小型暖通系统，设置一条从布局变化到性能变化的完整计算链。

| 实验步骤                     | 需要观察的证据                             |
| ---------------------------- | ------------------------------------------ |
| 建立原理模型与长度或阻力预算 | 预算在明确工况下能够支撑行为校核           |
| 给出两种粗布置               | 两种布置关联相同对象身份，变化有明确来源   |
| 提取等效参数并反注           | 参数关联布局版本，图纸随更新后的模型生成   |
| 重跑相关验证                 | 至少包含一个预期通过和一个预期不通过的反例 |
| 调整设计并重新验证           | 能说明调整了哪个承诺层级、为何足以解决问题 |

实验重点观察参数提取准确度、预算与实际值的对应关系、变化影响的覆盖率，以及计算与参考结果的差异。
根据这些结果修正提取器和行为模型，再用真实设备数据校准。

## 与既有文档的待协调关系

[ADR-0008](../adr/0008-six-stage-sysda-model.md) 仍采用六个承诺阶段，并将第三阶段称为“行为与容量”。
当前 UL 使用七项专业活动，且已将总容量确定、容量分配和原理设计的职责分开。
建议补充六个承诺阶段与七项专业活动的映射，统一容量归属和原理设计用语。
专业流程用于组织工作，承诺层级用于描述交付状态。

## 对产品的修改意见

- 在界面中同时展示设计版本、当前假设和结果适用性，帮助工程师辨认“已有模型”与“已有证据”。
- 将需求、参数、接口和验证项联结起来，使一次布局变化能够解释为何需要重新计算。
- 支持粗布置和部分行为等中间状态，让工程师随设计推进逐步补充信息。
- 优先实现一个能发现反例并支持修正的专业闭环，再扩大自动布局、综合和跨专业范围。
- 在正式交付入口汇集逐项证据和设计审查意见。
