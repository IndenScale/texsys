# 备忘录：专业协作、持续验证与 AI 授权

- 日期：2026-11-11
- 分类：可入库

## 用户最终明确的主张

用户先提出用仓库、issue、CI 和可自动运行的仿真组织工程协作，随后明确了组织方式：

1. monorepo 的优先场景是同一法人内部的多专业协作，例如综合性设计组织。
2. 跨法人协作通过 registry 和 package manager 引入、发布与更新依赖。
3. AI 可以承担复杂的包管理、Git 操作和提交说明整理；工程师关注工程决策及最终操作的检查授权。
4. 架构搜索和综合阶段尽可能放开探索；最终施工图报审时逐项开展设计审查。
5. AI 整理报审证据链和计算过程，工程师逐项审查并签核。

## 仓库组织与职责分工

同一法人内部，多专业可以围绕共同项目采用 monorepo 协作。
一个组织可以按项目、团队和资料可见范围设置多个仓库，各仓库内部保持共同版本管理。

| 机制           | 职责                               |
| -------------- | ---------------------------------- |
| 仓库组织       | 共同版本、变更关联、可复现输入     |
| 仓库和存储权限 | 管理资料的读取与修改范围           |
| 分支与合并请求 | 提出、比较和审查变更               |
| CODEOWNERS     | 指定文件对应的审查人员             |
| CI Gate        | 运行检查并根据结果控制合入         |
| 工程审查与签核 | 逐项检查设计和证据，形成发布结论   |
| 发布与采用记录 | 固定提供方发布版本和接收方采用版本 |

产品界面展示参与者、资料权限、审查分工和当前采用版本。

## 提资从文件搬运转为接口承诺

共享仓库减少复制和重复整理，专业间通过显式接口交换设计信息。
提资记录围绕接口定义、发布、接收、采用和变更影响组织。

一次接口交换至少应说明：

- 提供者、消费者、接口身份、版本和兼容条件。
- 采用的对象、单位、坐标参考及工况。
- 输入状态、假设、开放项和允许使用的范围。
- 发布内容摘要、相关证据和消费者采用关系。

同仓协作可以直接引用固定版本的接口；跨法人协作则可以把必要接口及证据发布为包。
跨法人包按接口需要组织数据、图纸和证据，提供方保留自身设计源。
既有[跨专业接口决策](../adr/0012-multidisciplinary-interface-contracts.md)已区分接口可用、版本兼容、设计批准和人工豁免。

## 语义冲突检测

用户关心的是 Git 字面冲突之外的工程冲突。
以可构造反例的工程约束建立检查集。

| 情况                     | 检查方法                         |
| ------------------------ | -------------------------------- |
| 设备能力与下游需求不匹配 | 接口容量和规定工况核对           |
| 端口介质或单位不一致     | 类型、单位与连接契约检查         |
| 布置变化影响行为         | 提取参数、重跑相关验证           |
| 独立变更共同消耗同一裕量 | 联合基线上的资源或约束检查       |
| 上游结果被下游继续引用   | 输入摘要、接口版本与采用关系检查 |

结果视图按检查项呈现通过、失败、缺数据、无法判断和求解错误，并显示已运行的规则与工况。

## 建议的持续验证分层

快速检查可在编辑和变更请求时运行，重计算可按影响范围、计划任务或显式请求执行。
各类模型按计算成本和变化频率设置触发方式。

| 层次     | 典型工作                             | 期望产出                   |
| -------- | ------------------------------------ | -------------------------- |
| 编辑反馈 | 模式、身份、单位、引用和基础连接检查 | 及时定位输入错误           |
| 变更检查 | 语义差异、受影响接口和局部计算       | 说明此次变更的工程影响     |
| 定期回归 | 固定基线上的跨专业规则与代表性工况   | 发现累积变化和检测盲区     |
| 发布审查 | 完整适用检查、证据覆盖与逐项人工处置 | 对确定版本形成明确发布结论 |

依赖图用于选择局部检查，定期回归覆盖联合基线。
代理模型用于快速筛选，高保真计算用于分析关键候选。
仿真提供脚本入口，执行服务根据后端能力组织无人值守和并发任务。

## 探索放手与报审逐项检查

用户提出的两种强度分别对应自动探索和逐项报审。

探索阶段建议在明确任务、可修改范围和资源预算内自动生成候选、运行计算和淘汰反例。
候选保留输入与证据，失败和无法判断的结果用于调整搜索方向。

报审阶段应固定待审设计、依赖、依据与证据版本，并逐项呈现要求、计算结果和未决事项。
AI 可以整理目录、对齐引用、检查缺项并辅助解释；对关键结论的接受和风险处置由明确责任人完成。
报审后发生的设计变化关联到受影响条目，便于工程师继续审查。

## AI 操作应让工程师看见什么

1. 操作前说明目标对象、拟执行变化、依赖升级和可能影响的结论。
2. 将包管理、Git 操作和提交说明等机械步骤批量执行。
3. 展示语义摘要与原始差异，允许检查 AI 是否误解了工程意图。
4. 记录执行者、输入版本、动作、验证结果和授权所覆盖的具体内容。
5. 遇到并发修改时重新计算变更计划。
6. 提供恢复工作副本的方式，并保留已经形成的发布和审查历史。

AI 生成 commit message 概括变更，并关联工程差异、检查结果和设计理由。
工程师通过这些信息检查最终操作，并作出授权。

设计候选与验收依据分别版本管理，搜索记录关联采用的判据和参考用例。

## 当前基线与建议先验证的用例

[SDL 批量编辑契约](../../spec/sdl/03-design-edits.md)已有 inspect、plan、apply、输入修订和计划摘要机制。
[Studio 工作台契约](../../spec/studio/01-workbench.md)定义本地编辑与任务能力。

建议先在暖通系统中选择两个子系统之间的一条明确接口，构造“各自检查通过、合并后违反共同约束”的反例。
验证系统能否定位冲突、说明受影响的要求、产生可审查修正，并在固定输入上重新运行。
再验证同一变化分别通过人工操作和 AI 批量操作时，是否形成等价的设计与证据。
最后对一次包更新验证“可见、可比较、可拒绝、明确采用”的全流程，再扩大协作范围。
