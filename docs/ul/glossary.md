## 专业设计流程

专业设计流程描述单一工程专业在设计期开展的工作。各项活动可以按输入依赖并行和迭代，工程验证与跨专业设计协调贯穿设计过程。七项活动与六个设计承诺层级是不同维度，其映射及容量归属以 [ADR-0023](../adr/0023-design-commitments-and-professional-activities.md)为准；不得据此要求界面或计算按编号顺序推进。

| 活动                                     | 使用边界与主要输出                                                                                                                             |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 01 需求定义（Requirements Definition）   | 确定系统在规定工况下所需的总容量、空间、重量、可靠性、消防和能效等目标与约束，明确适用规范、等级和验收准则。                                   |
| 02 架构设计（Architecture Design）       | 确定技术路线、功能拓扑和子系统接口。把总容量分配到子系统和设备，确定设备台数、单机容量规格及满足既定需求的冗余配置。                           |
| 03 原理设计（Schematic Design）          | 在既定拓扑和容量配置上定义系统如何工作，包括介质与能量流向、运行模式、控制与联锁、启停及故障切换。用单线图、管路原理图和控制逻辑图等表达设计。 |
| 04 部件选型（Component Selection）       | 按规格、性能、尺寸、成本和接口兼容性比选候选型号。确认采用的部件，并将型号和参数绑定到项目实例。                                               |
| 05 物理设计（Physical Design）           | 确定设备位置和管线路由，校核空间占用、净空、安装与维护条件。布局或路由变化影响系统行为时，回到原理设计复核。                                   |
| 06 工程验证（Engineering Verification）  | 汇总各阶段的专业校核和 DfX 专项证据。把验证结果关联到要求、判据、工况和设计版本。                                                              |
| 07 跨专业设计协调（Design Coordination） | 从架构阶段开始交换提资、核对接口、处理冲突，并记录接口版本与采用关系。系统集成（System Integration）用于描述实施期的装配、联接和联调。         |

稳态 0D 容量由需求定义确定总量，由架构设计完成分配。原理设计以该容量配置为输入。瞬态响应或寄生效应暴露缺口时，原理设计可推导新增冗余、缓冲容量或其他性能规格。涉及容量分配或设备配置的变更反馈给架构设计，并按更新后的配置重新校核行为。原理图表达系统行为，分析与校核结果随相应模型和工况单独记录。 [原理图](../../spec/sdl/01-core-model.md#原理图)

「概要设计」描述方案的成熟度，可作为涵盖架构、原理、初步选型和粗布置的阶段名称。流程中的 03 使用「原理设计」。

### 专业校核与 DfX

专业校核按工程领域组织，如电气、热、流体、结构和消防。DfX（Design for X）按设计目标组织，可涵盖可制造与可装配、可施工与可安装、可维护与可更换、可测试与可调试。各专业按交付对象选择适用科目，并在各设计活动中落实相应约束。工程验证汇集各科目所需的跨专业证据。已设限值的目标按判据验证，优化目标用于比较方案。

### 设计发布

设计发布（Design Release）是交付里程碑。发布时固定本次交付范围内的模型、图纸和清单版本，关联验证证据、接口状态及经批准的开放项。交付要求涉及施工或部署时，同时审查相应的安装、实施或切换方案。 [基线准出门禁](../adr/0018-deliverable-semantics-and-baseline-gates.md#过程自由基线有门)

## 模块包组成

**模块包（Module Package）**是按模块身份、版本和适用配置组织的交付单元，供项目引用和评价。模块是工程设计对象，模块包汇集该对象的定义、可复用资源和验证依据。模块部件库管理模块内部的部件定义，可随模块包交付。资产清单 `module.toml` 位于模块入口旁。 [模块包目录与资产清单](../../spec/sdl/04-module-package.md) · [引入交付物](../rfc/0002-device-cell-module-deliverables.md#引入交付物)

| 组成                             | 交付内容                                                                                                                                                                                             |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 引入清单（Import Manifest）      | 记录模块身份、版本、适用配置和依赖。逐项记录已提供、待补或不适用及依据。引用模型或资产时固定版本或内容摘要，注明来源、用途和适用范围。                                                               |
| 模块定义（Module Definition）    | SDL 部件定义、内部实例和拓扑、参数、对外端口签名，以及对外端口到内部端口或网络的绑定。端口签名描述介质或信号类型、方向、适用单位与兼容条件。                                                         |
| 行为模型（Behavior Model）       | 描述模块在给定条件下如何工作的可计算模型。交付实现或固定引用、参数、求解接口、端口绑定、假设及适用工况。                                                                                             |
| 图纸资源（Drawing Resources）    | 可复用的符号定义、平面轮廓或生成规则，以及适用的视图配置。需要交付架构图、原理图或布置图时，可附能追溯到模块定义和资源版本的视图成果。                                                               |
| 工程几何（Engineering Geometry） | 设备包络、接管位姿、安装基准和检修净空等。声明单位、坐标基准、保真度及可支持的校核。平面轮廓可以独立交付，也可以按固定规则从工程几何派生。                                                           |
| 渲染资产（Render Assets）        | 按展示需要交付的场景资源，包括网格（Mesh）、渲染材质（Render Material）和纹理（Texture）。网格描述表面形状，渲染材质定义外观，纹理可提供颜色、法线等输入。工程校核使用具备相应用途和精度依据的几何。 |
| 能力边界与验证资料               | 结构不变式、带条件的能力限值、工艺角与工况角、适用的测试用例和证据。结论关联模块版本、配置、角点与断言。                                                                                             |

模型、符号定义、工程几何和渲染资产可以独立维护和版本化，由模块包引用，也可以随包交付。包中资源按用途选配，例如效果渲染所需的纹理可以独立替换，工程材料的密度和导热系数仍由相应的工程数据提供。 [引入交付物](../rfc/0002-device-cell-module-deliverables.md#引入交付物) · [场景与几何技术栈提案](../adr/0001-openusd-native-scene-geometry.md#决策)

### 视图、符号与图元

| 首选用语                      | 使用边界                                                                                                                                                                           |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 视图（View）                  | 按用途选择范围、展开层级和信息。架构图和原理图可以复用同一拓扑投影、符号和图面排版。原理图关联行为定义和关键参数，可通过随图数据或属性面板表达。                                   |

### 目录约定

`<source>` 和 `<build>` 分别取项目清单中的 `layout.source` 和 `layout.build`，默认是 `src/` 和 `build/`。采用默认值的项目可以按以下方式组织。

```text
project/
├── texsys.toml                 # 项目清单与设计依赖声明
├── texsys.lock                 # 设计依赖的锁定结果
├── src/                        # 项目源文件
│   ├── system.sdl.json         # 项目设计入口与实例
│   └── library/                # 项目维护的部件定义
│       ├── cells/              # 单元定义
│       ├── devices/            # 器件定义
│       └── modules/
│           └── pump-group/     # 模块目录
│               ├── pump-group.sdl.json
│               ├── module.toml # 模块资产清单
│               ├── assets/     # 模块随包资产
│               └── library/    # 模块部件库，可选
│                   └── cells/
├── assets/                     # 项目源资产
└── build/
    └── dependencies/           # 按锁文件还原的依赖
        └── <package-name>/
```

`cells/`、`devices/` 和 `modules/` 是两级部件库共用的分类目录，可按需建立。`modules/<名称>/<名称>.sdl.json` 是模块入口，入口旁可再建 `library/`。跨文件引用通过 SDL 文档显式声明。 [SDL 部件库引用](../../spec/sdl/02-json-exchange.md#部件库引用)

## 测试与验证

| 首选用语                     | 使用边界                                                                                                           | 定义来源                                                                                                                                             |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 动态分析（dynamic analysis） | 通过执行模型，观察其随时间或事件演进的响应。响应可作为测试断言的输入。                                             | [行为测试与仿真边界](../adr/0010-build-test-sim-and-package-boundaries.md#命令语义)、[暖通动态行为](../../spec/build/04-hvac-dynamics.md#入口与结果) |

| 工况（scenario）             | 描述一次求解适用的运行条件，可包括初始状态、边界条件、输入信号和事件时序。                                         | [暖通工况参数](../../spec/build/04-hvac-dynamics.md#工况参数)                                                                                        |

## 维护方式

1. **按语境维护。** 术语正文放在 `docs/ul/` 的词表中，由[目录索引](README.md)统一导航。专业或工作台的术语可在同一目录下单列词表，并标明与共享术语的关系。
2. **命名澄清与语义变更分开。** 只澄清命名时，直接更新词表及所触及的现行文档。改变对象身份、数据规则或工程承诺时，先用 [RFC](../rfc/README.md) 讨论；决策记录进 [ADR](../adr/README.md) 或 [DDR](../ddr/README.md)，规则进入 `spec/`，同次更新词表。未决项链接到 [开放问题](../open-questions.md)。
3. **代码和历史按原样引用。** 代码标识、CLI 选项、交换字段与历史资料保留原拼写。新增面向用户的文字使用首选词；兼容字段迁移由对应契约定义。首版由评审检查用语与语义是否一致。
