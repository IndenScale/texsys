# ADR-0015：采用受构建契约约束的 Hook Runner

- 状态：已接受
- 日期：2026-11-05
- 取代：无
- 被取代：无
- 补充：ADR-0013

## 背景

ADR-0013 将构建定义为目标特定的数据收集、推导、表示、检查与证据管线。实际交付需要接入现有脚本和外部工具，例如 BOM 检查器、IFC validator、USD 工具、商业排版引擎和企业内部校验程序。不同 target 需要在主要构建步骤前后执行这些工具。

若只提供任意命令执行能力，脚本可能隐式修改源输入、生成未声明依赖、修复权威产物、读取网络或当前时间，使 target 的输入、成功条件和确定性证据失效。若完全禁止外部命令，又会迫使核心吸收大量领域工具适配细节。

因此需要一个 Hook Runner，但其职责是执行构建契约中显式注册的外部节点，而不是成为绕过 target、profile、依赖和证据语义的通用脚本运行器。

## 决策

### Hook 是 target 管线中的受约束执行节点

`build` 支持 `pre` 和 `post` hook。Hook 绑定明确的 target 和执行阶段，是 ADR-0013 推导管线的一部分，不构成独立的通用任务系统，也不要求提供 `texsys run <任意命令>`。

一个 target 可以生成多个文件并包含内存中间模型，因此 hook 首先挂在 target 边界上，而不是挂在模糊文件路径上。Post hook 可以通过稳定 artifact ID 限定输入；不得依赖未经声明的 glob 匹配结果改变构建行为。

Target 的标准执行时序为：

```text
解析 target、profile、scope 和依赖
  → 全局输入与依赖锁检查
  → pre hooks
  → 数据收集、推导、排版与序列化
  → post hooks
  → target 最终检查与状态合并
  → 产物摘要与 build.json 证据
```

Post hook 位于最终检查和产物摘要之前，使其声明的附加产物、诊断和状态能够进入同一次构建结果。任何 hook 未闭环时，target 不得报告 `pass`；已生成的文件按 ADR-0011 标记为部分结果或诊断产物。

### Pre 与 post 具有不同的修改权限

Pre hook 用于输入检查、环境检查和准备本次运行的临时工作区。它可以读取权威输入、依赖快照和已解析上下文，可以写入独立 scratch 目录，但不得：

- 修改 `src/`、依赖锁、项目阶段或权威项目配置；
- 生成未声明的权威中间模型供后续步骤隐式消费；
- 改变已经解析的 target、profile、scope 或依赖图。

如果前置脚本生成后续构建所需的权威中间模型，该脚本实际上构成 derivation 或依赖 target，必须进入依赖图和输入证据，不能伪装成 pre hook。

Post hook 用于产物检查、外部校验和生成契约声明的附加报告。它可以读取主要构建步骤生成的产物并写入声明的附加产物，但不得静默改写已经生成的 BOM、USD、IFC 等权威产物，也不得补造缺失输入或掩盖主要步骤失败。

如果脚本需要规范化、修复或改写权威产物，该改写必须成为主要推导管线中的显式步骤，并重新执行后续检查和摘要计算，不能作为不可见的 post 副作用。

### Hook 必须显式声明并确定顺序

Hook 声明至少包含稳定 ID、target、phase、命令、输入、输出和超时。概念示例为：

```toml
[[build.hooks]]
id = "hvac.check-bom"
target = "hvac:equipment-bom"
phase = "post"
command = ["uv", "run", "check-bom"]
inputs = ["artifact:bom-data"]
outputs = ["build/hvac/bom-check.json"]
timeout_seconds = 60
```

该示例规定信息职责，不预设当前项目清单已经支持这些字段。具体交换模式还应表达声明来源、脚本或 entry point 版本、内容摘要和运行时要求。

`command` 使用参数数组，默认不经过 shell。确需 shell 语法时必须使用不同的显式执行类型，不得通过隐式字符串拼接、环境变量展开或 shell 猜测改变参数含义。

项目 hook 必须在项目配置中显式声明。领域包可以提供被选定 target 所需的 hook，并纳入该 target 的版本和锁定契约；不得因为包恰好安装在当前环境中，就自动向所有项目或 target 注入脚本。

同一 target 的多个 hook 按显式声明顺序串行执行。首版不根据插件发现顺序、文件系统顺序或本机并行调度隐式改变执行顺序，也不自动并行执行具有数据依赖的 hook。

### Runner 使用结构化上下文和结果协议

Hook 的 stdout 和 stderr 保留为运行日志，不承担完整机器协议。Runner 向 hook 提供结构化上下文，至少包括：

- project root、target、profile 和 scope；
- 已解析的输入、来源快照及其摘要；
- 当前阶段可消费的 artifact ID、路径和摘要；
- 声明的输出位置和独立 scratch 目录；
- hook ID、phase 和协议版本。

Hook 返回结构化结果，至少包括：

- `status`；
- 结构化诊断；
- 实际生成的声明输出；
- 开放项及其影响。

状态沿用 ADR-0011：

- `pass`：该 hook 负责的契约得到满足；
- `fail`：发现具有判定依据的规则违例；
- `indeterminate`：资料、接口或判定依据不足；
- `error`：命令无法启动、超时、崩溃、输出协议无效或后端执行失败。

进程非零退出且没有有效结构化结果时按 `error` 处理，不猜测其领域含义。Hook 返回的路径必须属于声明的 scratch 或构建输出范围，且实际文件存在；未声明输出不得自动成为权威构建产物。

主要步骤或 pre hook 未成功时，普通 post hook 默认不执行。需要无论成功失败均收集诊断的能力时，应使用单独的显式诊断模式；普通 post hook 不同时承担 cleanup、finally、结果修复和权威检查职责。

### 权威构建与外部诊断按密闭性分级

Hook 可能读取网络、当前时间、随机数、完整环境变量或用户主目录。记录脚本路径和文件摘要本身不能保证确定性，因此区分：

1. **权威构建 hook**：脚本、解释器或工具版本、输入、环境依赖和输出均受契约约束，可以影响权威产物或作为 target 的必要通过依据；
2. **非密闭诊断 hook**：可以访问显式声明的外部服务或本机状态，但必须标记为非密闭，其结果仅用于附加诊断。

非密闭诊断 hook 不得成为权威 target 获得确定性 `pass` 的必要依据。若外部不可复现数据影响权威产物，则该产物不得继续标记为确定性权威产物，target 也不得按确定性契约报告 `pass`；应将相应能力建模为带固定来源快照的输入或独立非权威交付。

Runner 对执行环境至少实施以下控制：

- 固定工作目录和参数数组；
- 环境变量允许列表，不无条件继承完整环境；
- 显式区域、时区、字符编码和临时目录约定；
- 超时、取消、输出大小限制和结构化协议校验；
- stdout、stderr 与机器结果分离；
- 脚本、解释器、工具及依赖版本记录。

需要网络、凭证或外部事实的 hook，应将固定响应或来源快照作为显式输入。密钥不得写入构建证据，日志中也需要按适配器规则防止泄露。

### Hook Runner 不是安全沙箱

Hook 与当前 Python 领域包一样，属于受信任的项目构建代码。工作目录、环境允许列表和输出路径检查用于提高可复现性和减少意外副作用，不构成对恶意代码的安全隔离。

运行不可信项目或依赖时，需要独立的操作系统级进程、文件系统、网络和凭证隔离。Hook Runner 不得仅凭路径校验或命令数组宣称能够安全执行不可信脚本。

### 构建证据与运行日志分离

`build.json` 按 target 记录：

- hook ID、phase、声明来源和执行顺序；
- 脚本或包版本、内容摘要、解释器或工具版本；
- 输入、输出及其摘要；
- 结构化状态、诊断、开放项和密闭性级别；
- 对最终 target 状态及权威产物的影响。

Stdout、stderr、耗时、进程 ID、开始和结束时间属于运行诊断日志，不进入要求字节确定的权威证据内容。日志和临时文件路径不得替代结构化诊断或产物摘要。

相同 target、profile、scope、权威输入、hook 代码与运行时锁定版本，应产生相同的权威产物和确定性证据。非密闭诊断的即时输出不得隐式改变这些内容。

## 备选方案

### 提供通用任意脚本运行命令

不采用。通用命令入口不能表达 hook 与 target、输入、产物和状态的边界，容易形成绕过构建契约的第二套执行系统。

### 允许 pre hook 自由修改项目输入

不采用。这会使 lint、依赖锁和输入摘要失效，也使构建结果依赖不可见修改顺序。需要生成权威输入时，应建立显式依赖 target。

### 允许 post hook 自动修复权威产物

不采用。静默修复会隐藏生成器缺陷，并使主要步骤、检查和摘要无法对应。修复必须成为显式推导步骤。

### 只通过进程退出码表达所有结果

不采用。退出码不足以区分规则违例、资料不足、工具错误和结构化开放项，也无法稳定传递产物和诊断。

### 自动执行所有已安装包发现的 hook

不采用。这会把本机环境变成隐式构建输入，扩大执行范围并引入意外副作用。

### 将 Hook Runner 作为不可信代码沙箱

不采用。没有操作系统级隔离时，这种声明会制造错误安全预期。

## 后果

### 收益

- 现有 BOM、IFC、USD、排版和企业校验工具能够接入统一 target 管线。
- Hook 的输入、输出、顺序和失败语义可检查，不再依赖隐式脚本副作用。
- 外部诊断与权威构建可以共存，同时保持确定性和证据边界。
- 项目与领域包可以扩展构建能力，而核心无需吸收每个外部工具的实现细节。

### 代价与风险

- 需要定义版本化 hook 协议、声明模式、结构化诊断和输出安全规则。
- 解释器、外部工具和环境锁定增加复现成本，跨平台命令需要显式适配。
- 非密闭 hook 的误用仍可能污染权威结果，需要契约检查和审查共同约束。
- Scratch、日志、密钥和外部快照需要生命周期与保密管理。
- 当前构建实现尚无 target 解析和 hook 协议，本 ADR 不表示这些能力已经可执行。

## 验证与复审

- Pre hook 在依赖和全局检查通过后执行，不能修改 `src/`、锁、阶段、target、profile 或 scope。
- Post hook 的声明输出进入最终检查和摘要；未声明输出、越界路径和缺失输出均不能成为权威产物。
- 同一 target 的多个 hook 按声明顺序执行，包安装顺序和文件系统顺序不影响结果。
- 对 `pass`、`fail`、`indeterminate`、`error` 分别验证状态合并；无有效结果的非零退出、超时和协议错误均为 `error`。
- 主要步骤失败后普通 post hook 不执行，部分产物不得报告 `pass`。
- 修改权威产物的 post hook 被拒绝；显式推导步骤修改后必须重新检查并计算摘要。
- 非密闭诊断可以附加运行信息，但不能成为确定性权威 target 的必要通过依据。
- 环境变量、时区、区域设置、脚本版本和外部快照能够按契约复现；运行耗时和日志不会破坏确定性证据。
- 引入首个真实 IFC、USD 或排版外部 hook 时，复审协议兼容性、工具锁定、跨平台行为和日志保密边界。
- 若未来需要不可信项目执行，另行设计操作系统级沙箱，不放宽本 ADR 的信任假设。
