# ADR-0012：采用接口契约支持多专业协同构建

- 状态：已接受
- 日期：2026-11-05
- 取代：无
- 被取代：无

## 背景

不同建筑类型、专业和交付体系使用不同的阶段命名，各专业也可能长期异步推进。暖通已经需要具体供电条件时，电气可能仍处于方案阶段；结构专业能够提供设备荷载接口，也不意味着施工图阶段已经完成。

如果使用单一 `current_stage` 或全局阶段顺序表达这些关系，会把专业的局部承诺误当成整个项目的统一步调。如果直接建立“暖通某阶段依赖电气某阶段”的规则，阶段改名、提前提供资料或局部交付都会破坏构建逻辑。

多专业构建需要独立的阶段记录和稳定的交付契约，使协同依赖落在实际所需数据与证据上，而不是落在阶段名称上。

## 决策

### 各专业独立记录设计阶段

项目按稳定的专业标识分别记录 `current_stage`，并关联提供该专业扩展的领域包。例如：

```toml
[disciplines.hvac]
current_stage = "hvac:concept"

[disciplines.electrical]
current_stage = "electrical:concept"

[build]
default_targets = ["hvac:equipment-layout"]
```

专业阶段可以独立前进、暂停或回退。核心不计算所谓的整体最早或最晚阶段，也不要求所有专业处于同名阶段。需要整体视图时，可以生成各专业和开放接口的投影，但该投影不是新的权威阶段状态。

`build` 不自动推进阶段，也不因产物生成成功而暗示选型、审批、采购或交付承诺已经形成。阶段变更必须作为独立的项目元数据变更被审查。

### 跨专业依赖使用接口契约

Target 声明自己需要或提供的接口契约。契约具有稳定、带命名空间的标识，并至少描述：

1. 数据模式、版本和兼容要求；
2. 必需对象、稳定身份、单位、坐标参考和适用条件；
3. 闭合状态、假设、开放项及其对使用结论的限制；
4. 提供者和消费者可检查的证据与内容摘要。

例如，暖通布局 target 需要 `power-supply` 契约，而不是需要“电气施工图阶段”。电气专业只要通过其当前 target 提供满足版本和闭合要求的供电接口，就可以支撑暖通构建。

Target 对契约的需求由领域包声明；具体由哪个专业 target 提供，则由项目显式绑定。概念上的绑定记录为：

```toml
[[interface_bindings]]
contract = "electrical:power-supply"
consumer = "hvac:equipment-layout"
provider = "electrical:power-layout"
```

绑定把消费者、契约和提供者关联起来，不要求消费者了解提供者的阶段名称。契约快照是源模型的投影和证据，不得成为脱离源模型独立编辑的第二事实源。

同一专业内部的 target 可以直接声明目标依赖；跨专业依赖必须经过接口契约，禁止以阶段先后或插件执行顺序代替。

### 构建依赖图与执行

一次构建从 ADR-0011 选定的 target 出发，沿契约绑定找到必要的提供者 target，形成有向依赖图：

```text
消费者 target
  → 所需接口契约
  → 项目绑定的提供者 target
  → 提供者自身的必要依赖
```

执行器按依赖顺序运行，同一 target 在一次构建中只执行一次，且不执行无关专业或无关插件。接口必须先由提供者生成并验证，再交给消费者。

缺少绑定、找不到提供者、接口版本不兼容、必需接口未闭环或依赖图存在环时，必须报告具体未闭环项或执行错误，不得跳过依赖后继续报告成功。

接口开放不必然阻塞构建。只有消费者 target 明确允许该开放状态时，构建才可闭环；开放项及其受影响的结论必须进入双方证据。消费者未声明接受的开放接口不能被视为已满足依赖。

### 变化传播与证据边界

接口证据至少关联提供者 target、消费者 target、契约标识与版本、输入摘要、接口内容摘要和生成物摘要。上游接口内容变化后，下游已有证据不得继续被视为当前有效；下游必须重建或显式重新确认兼容性。

内容摘要变化只证明需要重新评价，不自动表示语义不兼容，也不自动批准新接口。版本兼容、设计批准和人工豁免不得由内容相同或构建成功代替。

构建证据应能回答：

- 哪个专业在什么设计承诺下提供了接口；
- 哪个消费者使用了哪一份接口快照；
- 接口有哪些假设、开放项和适用边界；
- 上游变化会影响哪些下游产物和结论。

跨专业接口只传递设计期模型和证据。采购、审批、施工或资产状态需要各自的外部记录，不因接口生成成功而自动成立。

## 备选方案

### 所有专业共用单一 current_stage

不采用。单一字段无法表达异步推进、局部交付和专业回退，会迫使项目元数据失真。

### 建立全局阶段枚举和统一顺序

不采用。不同专业的阶段名称与粒度没有通用的全序关系，硬编码顺序无法适应不同项目交付体系。

### target 直接依赖其他专业的 stage

不采用。阶段名称不是稳定的数据契约，会造成不必要的阻塞，也无法检查接口内容是否真正满足消费者需要。

### 每次构建运行所有专业并自行寻找可用数据

不采用。这会扩大构建范围，形成隐式依赖和不可预测副作用，也无法判断缺失数据是否影响当前目标。

### 允许生成后的接口文件独立编辑

不采用。独立编辑会使接口与源模型分离，破坏变化传播和证据追溯。需要人工决定时，应修改权威源输入或形成显式批准记录。

## 后果

### 收益

- 各专业可以使用自己的阶段命名并独立推进。
- 跨专业构建只依赖实际需要的接口及其证据。
- 上游变化能够定位受影响的下游产物，避免陈旧证据继续报告成功。
- 构建范围由目标与依赖图决定，不再受插件安装顺序影响。

### 代价与风险

- 项目需要维护接口提供者绑定，领域包需要发布机器可检查的契约。
- 契约粒度过粗会造成不必要阻塞，过细则会增加版本与绑定管理成本。
- 接口兼容不能仅靠摘要判断，需要模式、单位和语义检查共同支持。
- 测试和示例需要至少两个专业或等效桩包，单一暖通闭环不足以验证协同语义。

## 验证与复审

- 使用两个具有不同阶段命名的测试专业，能够仅通过接口契约完成依赖构建。
- 提供者阶段改名但接口保持兼容时，消费者无需修改依赖声明。
- 缺失绑定、未知提供者、版本不兼容、开放接口未获接受和依赖环均有独立失败用例。
- 上游接口摘要变化会使下游证据失效或触发重建；无关专业变化不影响当前构建。
- 构建只执行选定目标及必要依赖，不自动修改任何专业阶段或源输入。
- 接口快照能够追溯到权威源模型，不能独立编辑后仍通过一致性检查。
- 出现首个真实跨专业项目时，复审契约粒度、兼容规则和人工批准边界。
