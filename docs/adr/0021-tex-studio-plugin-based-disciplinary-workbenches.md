# ADR-0021：Tex Studio 采用插件式多专业工作台架构

- 状态：已接受
- 日期：2026-11-05
- 取代：无
- 被取代：无
- 补充：ADR-0010、ADR-0012、ADR-0014、ADR-0016、ADR-0020

## 背景

texsys 已有 SDL、CLI、领域包和浏览器预览，但专业设计还需要场景编辑、器件建模、架构搜索、布局布线、检查、仿真、结果可视化和提资协同。不同专业的对象、操作方式与任务组织不同，单一固定界面无法充分表达这些差异。

工程项目还涉及项目管理、商务、采购、造价和供应链。这些领域也具有自己的对象、规则、流程和交付物，应与暖通、电气、结构等工程专业使用同一扩展机制，而不是不断作为特殊模块加入宿主。

需要明确 Studio 与工具链的关系、专业工作台的独立性，以及插件必须遵守的共同规范，避免各专业成为无法互通的孤立应用。

## 决策

### Tex Studio 是插件式工作环境

GUI 产品称为 **Tex Studio**；**texsys** 继续表示 SDL 的参考实现、工具链与生态。Tex Studio 早期规划 Electron 桌面端和 Web 端，两端遵循同一专业插件与项目契约，宿主能力差异通过显式适配处理。

Tex Studio 由通用宿主与专业插件组成：

```text
Tex Studio 宿主（Electron / Web）
  ├── 通用能力：项目上下文、专业发现与切换、文档与版本、任务与结果、协作接口
  └── 专业插件
        ├── 暖通、电气、结构等工程专业工作台
        └── 项目管理、商务、采购、造价、供应链等专业工作台
```

宿主提供共同机制；专业插件拥有本专业工作台及其功能组织。插件通过显式、版本化契约组合，不依赖加载顺序、隐式覆盖或专业间多继承。

### 每个专业拥有自己的工作台

各专业可以自行定义导航、页面、编辑器、工具、对象属性、任务流程和结果视图。不同专业不必使用相同的画布或页面布局，宿主不把全部专业功能压入固定通用界面。

专业可按需要提供场景编辑、器件与行为建模、架构搜索、布局布线、提资协同、检查、仿真启动和可视化。项目管理或商务专业也可以采用台账、计划、合同、清单和流程等适合自身的交互，不要求所有专业都具备建模或仿真能力。

共享编辑组件和跨专业联合视图可以复用，但不替代各专业工作台。联合视图引用同一对象身份及其所属专业，不复制事实，也不授予对其他专业数据的隐式修改权。

### 管理与商务领域同样属于专业

项目管理、商务、采购、造价、供应链与工程专业具有同等的插件地位，分别拥有自己的领域对象、规则、记录与工作台。具体专业拆分由插件声明和领域契约确定，宿主不硬编码固定专业列表。

宿主的通用项目上下文负责项目身份、工作空间关联和公共访问机制；立项、计划、里程碑、责任与标段划分等业务能力由项目管理专业定义。合同、采购、计价和供应链事实由相应专业或其声明的外部权威来源维护。

专业间通过稳定引用、快照与显式映射关联。例如，设计实例、采购项、计价项和实际资产可以有关联，但不强制采用同一身份或同一层级。设计通过不自动形成商务批准、采购事实或现场验收事实，沿用 ADR-0014 的证据边界。

### 启动时发现专业，并提供切换入口

启动时根据当前宿主实际包含、已启用且契约兼容的插件发现专业。存在可用专业时，界面提供明确的专业入口与切换方式；仅有一个专业也应标识当前专业。

切换专业保留当前项目上下文，并按对应插件进入其工作台。未保存编辑必须有显式保留或处理机制，切换不得静默丢失源修改，也不得隐式取消已提交的后台任务。

未安装或未包含的专业不显示为已可用。插件加载失败、版本不兼容或执行能力缺失需要明确诊断；专业可加载但某个求解后端不可用时，应明确标记受影响功能。没有可用专业时，宿主显示空状态和诊断，不伪造默认专业。

本决策要求启动发现与运行期间的专业切换，不要求实现插件热安装或热更新。

### 专业内功能自由定义，但必须遵循共同契约

以下是专业插件接入 Tex Studio 的最低规范要求。具体清单与 SDK 格式在 [OQ-16](../open-questions.md#oq-16) 中跟踪。

| 契约           | 必须遵循的要求                                                                                                                              |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 身份与声明     | 声明插件及专业的稳定 ID、命名空间、版本、宿主兼容范围、依赖和能力；入口与扩展点显式注册，冲突明确失败，不能后加载覆盖                       |
| 宿主与生命周期 | 通过公开宿主接口访问项目、文档、任务和共享服务；声明所需宿主能力与访问范围，支持加载、切换、退出及失败诊断                                  |
| 数据与版本     | 领域数据采用版本化模式，明确对象身份、来源、单位、坐标参考和状态的适用要求；模式不兼容必须诊断或显式迁移                                    |
| 编辑与事实归属 | 明确模型、外部事实、工况、图面排版和结果各自的权威来源；持久修改形成可审查变更，处理撤销与外部修改冲突，生成物不能静默反写为源事实          |
| 文本与自动化   | 持久工程数据、问题定义和计算配置具有公开、可检查的表示或显式资产引用；核心领域操作和计算提供可编程入口，允许 GUI、CLI 与 Agent 复用领域能力 |
| 任务与执行     | 耗时计算接入共同任务与结果契约，声明输入快照、依赖、执行环境和后端；记录状态、日志、产物与取消能力，区分执行完成、检查通过和工程接受        |
| 结果与可视化   | 结果关联输入版本、语义对象、变量及适用条件，保留单位和诊断；旧结果可查看但不能冒充当前有效结果，前端展示不得另立一套冲突的领域事实          |
| 提资与协同     | 跨专业交换使用显式版本化接口、固定提资快照与采用关系，沿用 ADR-0012；发布、接收、接受与采用分别记录，上游变化触发下游影响识别与复核         |
| 兼容与验证     | 插件提供能力声明对应的契约验证与最小可重跑示例；缺失、未知、不适用和失败不得冒充通过，两端能力差异必须显式报告                              |

规范按插件声明的能力适用：没有求解功能的插件不必提供求解器，没有空间数据的专业不必声明坐标系；共同的身份、兼容性、事实归属与诊断纪律始终适用。

已有 Python 领域包与未来 Studio 插件可组合复用。一个专业插件可以依赖多个模型、检查或求解包；后台包被发现不自动表示已经存在 GUI 工作台，二者通过明确声明关联。

### 与现有架构及实现范围的关系

本决策接受多专业 Studio 的产品与扩展架构，不表示上述插件、编辑器、任务宿主或提资流程已经实现。当前可执行能力仍以 [进度审查](../progress.md) 为准，暖通冷启动的当前工程验收仍以 [范围文档](../scope.md) 为准。

ADR-0010 的领域包、ADR-0012 的跨专业接口、ADR-0016 的显式契约组合和 ADR-0020 的工程计算／图形呈现分工继续有效。各专业拥有工作台不改变 SDL 的设计语义边界，也不要求合同、订单和审批记录进入 SDL 核心。

Electron 与 Web 的共享 SDK、宿主适配以及任务／协作交换协议分别在 [OQ-16](../open-questions.md#oq-16) 和 [OQ-17](../open-questions.md#oq-17) 定义后实施，不从本决策推断已经存在远程执行服务。

## 备选方案

### 所有专业只能使用同一固定界面

不采用。专业的对象与交互存在实质差异，固定画布和导航会限制场景编辑、器件建模及管理业务。共同契约统一协作方式，专业工作台保留交互自主性。

### 每个专业独立建设完整应用

不采用。项目、身份、版本、任务与提资机制会重复建设并产生漂移，跨专业切换与联合协调难以形成连续工作流。

### 管理、商务和采购全部固化到宿主核心

不采用。这会让宿主不断吸收领域对象与业务流程，并使工程专业和管理专业采用两套扩展机制。

### 插件任意操作数据，仅统一菜单入口

不采用。菜单聚合不能保证事实归属、版本、后台执行或提资可追溯，插件必须遵守公开、可验证的共同契约。

## 后果

- 各专业能够提供适合自己的完整工作台，并共享项目上下文、任务与协作机制。
- 管理与商务领域可以独立扩展，不要求修改宿主核心或污染 SDL 语义。
- 需要维护插件清单、宿主 SDK、数据模式、版本兼容和能力验证，增加平台工程成本。
- 专业自治可能造成导航和操作习惯差异；公共操作遵守宿主约定，领域操作保留专业表达。
- Electron 与 Web 的运行条件不同，需要显式适配与诊断，不能仅凭共享前端声称功能等价。

## 验证与复审

- 至少用一个工程专业和一个管理／商务类专业验证独立工作台及同等插件地位，宿主不增加专业专属分支。
- 验证启动发现、专业切换、空状态、重复注册、版本不兼容和加载失败；切换不丢失编辑或后台任务。
- 两个专业能够通过稳定引用与接口快照交换信息，保留各自权威来源，并识别提资变更的下游影响。
- 同一领域操作能从 GUI 与可编程入口产生一致的工程变更或结果；不同宿主上的缺失能力有明确诊断。
- 带计算能力的插件验证后台执行、输入快照、结果关联和独立检查，不能以任务完成代替工程通过。
- 在实现首个 Studio 插件、引入新的宿主或改变公共契约时复审；具体前置问题见 OQ-16、OQ-17。
