# ADR-0006：分离设计依赖的声明、锁定与同步

- 状态：已接受
- 日期：2026-11-04
- 取代：无
- 被取代：无

## 背景

SDL 项目会引用部件库、规则包和其他设计资产。仅声明依赖名称不足以复现一次设计运行；把依赖直接复制进 `src/` 又会混淆用户源输入与外部资产。当前 `texsys.toml` 只描述项目身份和布局，`texsys.lock` 仅为预留名称，尚无真实解析行为。

首个实现需要形成完整而有限的闭环，不在没有仓库协议和版本兼容规则时伪造通用包管理器。

## 决策

1. 设计依赖与 Python／Node 实现环境分离。`pyproject.toml`、`uv.lock`、`package.json` 和 `package-lock.json` 继续由 uv／npm 管理，`texsys` 不修改它们。
2. 第一版只支持本地路径包。被引用包必须有合法 `texsys.toml`，并在 `[project]` 中声明非空 `version`。根项目自身可以不声明版本。
3. 根项目在 `[dependencies]` 中声明直接依赖，例如 `name = { path = "../name" }`。可选 `version` 只表示精确版本约束，不引入版本区间。
4. 解析器递归读取路径包的直接依赖，检测名称冲突、精确版本冲突和依赖环。只有完整解析成功后才生成锁文件。
5. `texsys.toml` 是依赖意图的权威来源；`texsys.lock` 记录完整解析结果，包括根依赖声明摘要、每个包的名称、精确版本、相对路径、传递依赖和源内容 SHA-256 摘要。锁文件不写入时间戳。
6. 内容摘要覆盖包清单、`src/` 与 `assets/` 中的文件相对路径和字节内容。符号链接、缺失包、非法布局及无法读取的输入均使解析失败。
7. `texsys lock` 只解析并写锁文件，不同步包内容；`lock --check` 只比较当前解析结果，不写文件。
8. `texsys sync` 严格读取现有锁文件，验证根依赖声明和每个包的内容摘要，再把包还原到 `build/dependencies/`。锁文件缺失、声明变化或源内容变化时失败，不静默重新锁定。
9. `texsys add PATH` 与 `texsys remove NAME` 分别修改直接依赖声明、重新锁定并同步。解析失败时清单和锁文件保持不变；同步只替换 texsys 管理的依赖目录，不删除用户源文件或全局缓存。
10. `sync` 通过 staging 目录整体替换项目依赖视图，避免留下半套依赖。清单和锁文件采用同目录临时文件原子替换。
11. 远程仓库、版本区间、私有凭据、内容寻址全局缓存和跨包 SDL 引用不属于本决策的首个实现范围。

## 备选方案

### add 只修改清单，不解析和同步

不采用。命令成功但依赖不可用会让用户误以为项目已经可运行。`lock` 已提供只解析的独立入口。

### sync 自动更新过期锁文件

不采用。同步如果改变解析结果，CI 就无法区分还原既有基线与接受新依赖。

### 在 src 中复制依赖

不采用。`src/` 是项目权威源输入，外部包应位于可重建且默认忽略的管理目录。

### 第一版实现通用 registry 和语义版本区间

不采用。当前尚无仓库协议、兼容矩阵和可信来源策略，提前实现只会固化未经用例验证的假设。

## 后果

### 收益

- 依赖意图、完整解析和本机落地三种状态可分别检查。
- 本地与 CI 可以依据同一内容摘要还原依赖，源内容漂移会显式失败。
- 路径包足以支撑暖通切片和离线端到端测试。

### 代价与风险

- 路径包适合单仓库和受控工作区，不等于可公开分发的包生态。
- 内容变化要求显式重新锁定，这是有意的审查成本。
- 当前没有跨包 SDL 引用解析；同步成功只说明依赖内容已还原，不证明模型语义有效。

## 验证与复审

- 直接依赖、传递依赖、删除、重复同步和无变化锁定均有自动化测试。
- 依赖环、名称冲突、版本冲突、内容漂移和缺失锁文件均失败且不产生成功锁文件。
- `lock --check` 不写文件，`sync` 不改清单或锁文件。
- 出现第一个远程包来源或版本区间需求时，新增 ADR 定义来源信任、兼容和升级策略。
