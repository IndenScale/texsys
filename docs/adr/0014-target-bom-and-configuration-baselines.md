# ADR-0014：采用目标 BOM 与配置事实快照

- 状态：已接受
- 日期：2026-11-05
- 取代：无
- 被取代：无
- 补充：ADR-0013

## 背景

ADR-0013 已确定 BOM 不以完成选型为前提，并使用显式 profile 区分交付深度。进一步设计需要覆盖可研、工程设计、采购、建成和维护中的设备清单。这些清单都可称为 BOM，但其权威来源和现实含义不同：

- 可研和工程设计主要表达规划假设、功能规格、设计配置与数量；
- 采购 BOM 表达订单或合同实际约定的产品、配置与数量；
- 建成 BOM 表达现场实际安装、验收和替代情况；
- 维护 BOM 表达某一生效时点仍然有效的维护、改造和更换配置。

若把这些状态放入单一线性的 `maturity` 字段，会把设计深入程度与生命周期事实混为一谈，并错误暗示 `as-maintained` 是比 `as-built` “更成熟的设计”。项目的不同设备也可能同时处于设计、采购、安装和维护状态，整份清单不能天然只有一个事实状态。

需要一种目标 BOM 结构，使不同交付契约共享身份与映射，同时保留各自的来源、范围、时点和证据边界。

## 决策

### Target BOM 是带契约的投影与快照

Target BOM 是针对明确用途和统计范围生成的设备或物料投影，不是 SDL 中独立维护的第二事实源，也不是简单表格文件。其概念信息结构为：

```text
Target BOM
├── target                 交付目标
├── profile                交付与证据契约
├── scope                  系统、区域、设备和其他统计边界
├── source_snapshots       权威设计或外部事实快照
├── entries                设备或物料行及逐行依据
├── mappings               设计、采购、物理资产等对象映射
├── open_items             开放项及其影响
├── views                  聚合、筛选、分片、排序和比较视图
└── evidence               检查、摘要、来源和适用边界
```

该结构规定信息职责，不预设当前 JSON 交换子集已经实现这些字段。具体交换模式应版本化，并保持 target、profile、view 和 evidence 的边界。

Target BOM 可以由多个权威快照投影形成，但不得把不同来源静默拼接成一个无法追溯的统一事实。每一行及其关键属性都应能追溯到相应来源。

### 使用五类 profile，不使用线性 maturity

首版 Target BOM 支持以下稳定 profile 标识：

| Profile         | 中文名称     | 主要权威依据                   | 闭环重点                                       |
| --------------- | ------------ | ------------------------------ | ---------------------------------------------- |
| `feasibility`   | 可研 BOM     | 规划需求、系统架构与显式假设   | 设备族、功能规格、数量、备用策略、范围和状态   |
| `engineering`   | 工程 BOM     | 实例级设计模型、计算与技术规格 | 技术参数、设计配置、实例关系、映射和设计开放项 |
| `as-purchased`  | 采购事实 BOM | 合同、订单和采购配置快照       | 实际厂家、型号、订单配置、数量及相对设计的偏差 |
| `as-built`      | 建成事实 BOM | 安装、验收、竣工和现场记录     | 实际安装实例、位置、配置、替代和现场偏差       |
| `as-maintained` | 维护事实 BOM | 维护、改造、更换和资产记录     | 当前有效配置、替换关系、维护变更及生效时间     |

这些标识不构成可比较大小的成熟度序列。核心不得定义 `feasibility < engineering < as-purchased < as-built < as-maintained`，也不得据此自动批准、推进或回退项目状态。

`engineering` 是一个可扩展的工程设计 profile 族入口，具体专业应通过版本化契约声明所需技术字段和检查，而不是由核心假设所有专业具有相同详细程度。

Profile 表示本次交付范围内必须满足的最低契约。任何 profile 的 `pass` 只对该范围和契约有效，不自动证明后续生命周期事实，也不替代设计审查、采购审批、现场验收或维护确认。

### 全局 profile 与逐行事实依据分离

Target BOM 的 profile 约束本次交付，不声称所有设备天然处于同一生命周期状态。每一行应具有独立的 `item_basis`，至少能够表达：

1. 依据类型：规划、设计、采购、安装、竣工或维护记录；
2. 来源快照、对象标识和内容摘要；
3. 已知、假设、待定等参数状态及选型状态；
4. 适用条件、生效时间和记录版本；
5. 与相关设计或外部实现对象的映射；
6. 未解决差异和开放项。

项目可以只针对长周期设备生成 `as-purchased` BOM，同时让其他设备继续处于工程设计。此时统计范围必须显式限定为已要求采购闭环的设备，不得把局部采购 BOM 提升为整个项目的采购事实。

范围内必需行缺少该 profile 所需依据时，不得通过降低字段要求或借用其他行的事实报告 `pass`。资料不足按 ADR-0011 报告 `indeterminate`；可以显式缩小 scope 或选择符合当前交付目的的 profile，但不得自动降级。

一行可以附带比当前 profile 更晚或更具体的证据，但这只增强该行的可追溯性，不改变整份 BOM 的 profile，也不证明其他行具有同样事实。

### 外部事实只能由证据快照支持

`feasibility` 和 `engineering` 主要从权威设计模型投影。`as-purchased`、`as-built` 和 `as-maintained` 必须消费相应外部系统或经确认记录的快照，不能仅依据设计模型中的厂家、型号、位置或计划数量生成。

`texsys build` 可以检查快照的结构、身份映射、内部一致性和 target 闭环，但不能仅凭构建成功证明订单真实、现场已经验收或维护记录获得授权。来源认证、审批和法律效力保留在相应证据系统或其适配边界中。

外部事实以明确快照进入构建。快照至少关联来源、记录版本、内容摘要和适用时点；构建不得在后台隐式读取不断变化的“当前状态”而仍声称结果可复现。

运行期维护事实可以回流形成新的 Target BOM 和设计复审证据，但不得静默回写设计意图。证据、审批和运行记录的通用归属继续受 OQ-9 约束，本 ADR 不要求把所有外部记录存入 SDL。

### 设计实例与物理资产分别标识

Target BOM 至少区分以下身份：

- `design_instance_id`：项目设计中的实例或具有稳定身份的功能组；
- `procurement_item_id`：合同、订单或采购包中的对象；
- `physical_asset_id`：实际安装、验收或维护的物理资产。

这些身份通过显式映射关联，不强制一对一。可研设备组可以展开为多个设计实例，一个成套采购项可以对应多个设计功能，一个物理成套设备也可以实现多个设计角色。映射应记录关系类型、来源、版本、状态和开放项，沿用 ADR-0009 的设备映射规则。

设备维护更换时，若功能位置和设计承诺不变，新的 `physical_asset_id` 可以替换旧资产并保留历史关系；不得通过覆盖旧资产标识抹除历史。若功能、容量、接口或设计承诺改变，应形成设计变更和复审，不能只作为同型号维护替换处理。

采购、建成和维护快照追加为新的配置事实版本，不覆盖早期设计或历史事实。当前有效配置由明确的生效记录和快照推导，而不是依赖文件被反复原地修改。

### 配置差异需要显式比较而非静默合并

不同 profile 或同一 profile 的不同快照可以进行受控比较，例如：

```text
engineering   ↔ as-purchased   选型、数量、配置和采购替代差异
as-purchased  ↔ as-built       安装位置、现场替代和数量差异
as-built      ↔ as-maintained  维修、更换、改造和失效资产差异
```

比较结果至少区分新增、移除、替代、数量变化、配置变化、位置变化和映射变化，并关联原因、证据及复审状态。差异不自动等于错误，也不自动获得批准；只有违反当前契约且已有判定依据时才报告 `fail`。

比较和回流不得静默修改任何一侧的权威记录。需要改变设计意图时，应产生独立设计变更；需要纠正外部事实时，应在相应来源系统形成新记录。

### 成熟度仅作为派生视图

管理视图可以根据明细派生已确认规格比例、已选型比例、已采购或已安装数量比例、假设项数量、开放项数量和配置偏差数量。

这些指标用于汇总和观察，不是权威 `maturity` 字段，不得驱动隐式检查分支。指标必须说明统计范围、分母、身份去重规则和来源快照，不能用一个百分比替代具体未闭环项。

BOM 的聚合、分片和单位规则继续遵循 ADR-0013。不同事实依据的数量不得在未说明映射和计量规则时直接相加，价格仍由独立商务契约处理。

### 证据与确定性边界

Target BOM 证据至少记录：

- target、profile 及其契约版本；
- 统计范围、排除项和视图规格；
- 设计与外部来源快照、摘要、版本和适用时点；
- 逐行依据类型及设计、采购、资产映射；
- 必需检查、派生指标、开放项和差异；
- 生成后端、产物摘要和适用范围。

相同 target、profile、scope、视图规格、来源快照和后端版本，应产生相同的权威 Target BOM 与确定性证据。所谓“当前采购”“当前建成”或“当前维护”必须先解析为明确快照，不能以构建机器当前时间或在线系统即时状态作为隐式输入。

## 备选方案

### 使用单一线性 maturity 字段

不采用。设计深入程度、选型承诺和生命周期事实是不同维度，线性字段会制造虚假的先后关系，并隐式混合检查规则。

### 为每种状态独立维护一份设备清单

不采用。独立事实副本容易造成身份、数量和配置漂移。Target BOM 应共享映射并引用各自权威快照。

### 要求整份 BOM 的所有行具有同一状态

不采用。实际项目通常按设备包和区域异步推进，强制统一状态会导致虚假采购或安装声明，或使局部有效交付无法闭环。

### 将采购、施工和维护记录全部并入 SDL

不采用。SDL 保持设计期权威边界，Target BOM 通过快照和映射消费外部事实，避免把设计模型变成订单、现场和维护系统。

### 发现差异后自动回写设计模型

不采用。现场差异可能合理，也可能需要整改或设计变更；自动回写会破坏设计意图、审批和历史证据。

## 后果

### 收益

- 可研、工程、采购、建成和维护 BOM 具有明确且互不冒充的语义。
- 项目能够按设备包和范围异步形成有效交付，不必伪造统一成熟度。
- 设计实例、采购项和物理资产可以跨生命周期追踪，设备替换不会抹除历史。
- 配置差异、开放项和派生成熟度指标能够接受审查，而不是隐藏在表格覆盖或百分比中。
- 固定快照使 Target BOM 可以复现，并界定设计工具能够证明和不能证明的事实。

### 代价与风险

- 需要采购、竣工和维护适配器，以及稳定的来源快照和身份映射机制。
- 多对多映射、记录版本、生效时点和差异分类增加交换模式与审查成本。
- 外部记录可能不完整或失真，结构检查通过不能替代来源认证和现场核验。
- Profile 版本需要长期维护；过宽的要求会阻塞局部交付，过弱的要求会制造形式上的闭环。
- 当前 JSON 交换子集尚未实现完整 Target BOM、映射和快照语法，本 ADR 不表示这些能力已经落地。

## 验证与复审

- 以 2 台 40 MW 和 1 台 100 MW 机组生成 `feasibility` BOM，无具体型号时可以通过；相同设计输入不得在无采购快照时通过 `as-purchased`。
- 长周期设备能够在显式 scope 内形成 `as-purchased` BOM，其他设备保持 `engineering`，不得自动提升整个项目状态。
- 范围内必需行缺少采购、安装或维护依据时得到 `indeterminate`，不得借用其他行证据或自动降级通过。
- 一个采购项对应多个设计实例、一个成套资产对应多个功能角色时，数量汇总和身份映射保持正确且不重复计数。
- `as-built` 中的现场替代保留设计、采购和物理资产身份及差异，不自动修改设计意图。
- `as-maintained` 中设备更换生成新的物理资产映射和历史快照；功能或容量改变时触发设计变更要求。
- 对相同来源快照重复构建得到相同 Target BOM；来源系统在线状态或构建时间不会在无显式输入时改变结果。
- 派生成熟度指标声明范围、分母和去重规则，其变化不得隐式改变 profile 检查。
- 引入首个采购适配器、竣工回流或维护系统集成时，复审来源认证、快照版本、差异分类和证据所有权。
