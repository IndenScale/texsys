# ADR-0011：采用按阶段解析目标的分阶段构建

- 状态：已接受
- 日期：2026-11-05
- 取代：无
- 被取代：无
- 补充：ADR-0010

## 背景

ADR-0010 将 `build` 定义为从锁定输入确定性生成产物和构建证据，但没有规定一次构建的范围。当前参考实现调用所有已安装包的 `build()`，更适合输入已经齐备的冷站最小闭环。

实际工程项目可能长期处于方案、架构或初步设计状态，尚未完成选型、招投标、详细布局或采购绑定。如果 `build` 以整个项目最终完成为目标，早期项目将无法构建；如果以“尽力生成能够生成的内容”为目标，`pass` 又无法区分完整闭环、合理开放项和静默缺失。

需要把设计阶段、构建范围和构建成功标准分开，同时保持 ADR-0010 对确定性、证据和命令边界的约束。

## 决策

### 构建以显式目标的闭环为成功标准

`build` 的成功语义是：**完成本次选定 target 所声明的范围闭环，而不是完成整个项目，也不是尽力生成部分产物。**

Target 是具有稳定标识的构建契约，至少声明：

1. 所需输入及其适用范围；
2. 必须生成的模型、场景、文本、投影或其他产物；
3. 必须通过的全局检查和目标范围检查；
4. 允许保留的开放项及其表达形式；
5. 对其他 target 或接口契约的依赖。

Target 可以对应阶段、专业、子系统或交付物，不强制与设计阶段一一对应。闭环只针对选定 target 及其依赖，不要求选型、采购、施工或全部专业已经达到最终状态。

未知、假设和未确认值可以存在于已闭环构建中，但必须显式表达，并说明其影响的产物和结论。静默省略必需输入、跳过必需产物或把未执行检查记为通过，均不构成闭环。

### 通过 target 选项显式选择范围

`texsys build` 增加可重复的 `--target TARGET`。重复出现时，构建选定 target 的集合并合并其必要依赖，同一 target 只执行一次。

未指定 `--target` 时，按以下顺序解析：

1. 项目元数据中的 `build.default_targets`；
2. 项目 `current_stage` 到默认 target 的显式绑定；
3. 无法得到唯一、无歧义的 target 集合时拒绝构建并要求显式指定。

多专业项目具有多个阶段记录且没有 `default_targets` 时，不得擅自把所有阶段都解释为构建范围。默认解析不得退化为“运行所有已安装插件”。

CLI 必须输出解析后的 target 及其来源。构建证据必须记录同样的信息，使一次构建能够在不依赖隐式本机状态的情况下被解释和复现。

### 阶段与构建目标保持分离

Stage 表示项目或专业当前已经作出的设计承诺；target 表示一次构建必须闭合的契约。`current_stage` 只用于选择默认 target，不直接驱动分散在插件中的隐式分支逻辑。

领域包可以定义自己的 stage 和 target。标识使用稳定命名空间，例如：

```text
sysda:architecture
hvac:concept
hvac.cn:scheme-design
electrical:concept
```

面向用户的阶段名称可以本地化，内部标识不随显示语言变化。核心不根据名称、字典序或编号比较不同领域阶段的先后，也不要求领域阶段采用 ADR-0008 的六阶段名称。

ADR-0008 的六阶段继续作为通用承诺层级和证据边界；领域可以建立自己的阶段命名及到默认 target 的绑定。跨专业协同不按阶段排序，具体规则见 ADR-0012。

### 构建执行与结果状态

构建只执行选定 target 及其必要依赖，不再以“所有已安装包”作为隐式执行范围。设计依赖仍须通过锁检查；构建不自动更新锁、不同步依赖、不修改 `src/`，也不自动推进任何 `current_stage`。

输入语法、身份、路径安全和依赖完整性等全局检查必须通过。领域语义和交付闭合检查按 target 范围执行；与目标无关的未完成工作不得阻塞构建，影响所选输入或产物的错误不得忽略。

构建结果沿用状态化证据语义：

- `pass`：所有选定 target 均满足其闭环契约；
- `fail`：输入或产物违反已具备判定依据的闭环约束；
- `indeterminate`：必需资料、接口或判定依据不足，无法完成或判断闭环；
- `error`：工具、插件或后端执行失败。

诊断过程可以保留已经生成的部分产物，但必须标记为部分结果，不得报告 `pass`，也不得作为已闭环的权威交付物消费。部分产物是否保留不改变本次构建的失败或无法判断状态。

### 构建证据

`build.json` 至少记录：

- 请求和最终解析的 target 集合及解析来源；
- 关联的专业、stage、领域包名称和版本；
- 输入文件摘要和依赖锁信息；
- 实际执行的目标及依赖关系；
- 产物路径、摘要和适用范围；
- 显式开放项、未闭环项及各检查的状态；
- 所消费的跨专业接口证据，按 ADR-0012 记录。

相同目标、输入、锁和包版本必须产生相同的权威产物与确定性证据内容。构建成功不表示整个项目完成、测试通过、仿真通过或现实建造完成。

## 备选方案

### 以整个项目最终完成作为 build 的成功条件

不采用。这会使早期架构和方案模型无法形成可复现产物，也把设计成熟度与构建执行混为一谈。

### 以尽力而为作为 build 的成功语义

不采用。下游无法区分合法开放项、输入不足和插件漏生成产物，`pass` 会失去稳定契约。部分生成只能作为明确标记的诊断能力。

### current_stage 直接控制插件内部行为

不采用。隐式分支会使构建范围难以审查和复现。阶段只选择具有显式契约的默认 target。

### 核心规定一套全局阶段名称和顺序

不采用。不同建筑类型、专业和交付体系具有不同命名与并行关系，全局编号会制造不存在的先后依赖。

## 后果

### 收益

- 早期项目可以完成与当前设计承诺相匹配的构建闭环。
- 构建成功、项目成熟度和部分产物具有不同且可检查的语义。
- 默认构建行为可从项目元数据解释，并在证据中复现。
- 领域可以扩展阶段与交付目标，而不污染核心阶段模型。

### 代价与风险

- 项目需要维护阶段到 target 的绑定，多专业项目还需要显式默认构建范围。
- 插件声明过弱的 target 可能制造形式上的闭环，需要契约审查和一致性测试。
- 全局检查与目标范围检查的划分必须稳定，不能由插件随意缩小安全约束。
- 现有未声明阶段或默认 target 的项目，在引入该语义后需要显式指定 `--target` 或补充元数据。

## 验证与复审

- 架构 target 在未完成选型和采购时能够闭环；采购 target 在相同输入下不得误报成功。
- 覆盖 CLI target、`default_targets`、阶段绑定和无法唯一解析的优先级与失败测试。
- 显式开放项可以闭环，静默缺失必需输入或产物不能闭环。
- 与目标无关的未完成专业不阻塞构建；真实必需依赖缺失必须可见。
- 重复构建保持权威产物字节一致，不修改源输入或阶段元数据。
- 自定义阶段命名空间冲突、未知 target 和缺失绑定均显式失败。
- 引入第一种具体领域阶段映射或部分构建 CLI 时，复审 target 契约和结果状态是否仍保持一致。
