# ADR-0017：采用契约组合的系统原理图投影、图元解析与渲染

- 状态：已接受
- 日期：2026-11-05
- 取代：无
- 被取代：无
- 补充：ADR-0013
- 后续：ADR-0018（首个 target 更名为 `hvac:system-schematic`，原理图的信息承诺修订为组成＋拓扑＋行为；本 ADR 其余决策不变）

## 背景

ADR-0013 已将原理图构建分为拓扑、排版和渲染，但还缺少可实现的绘图交换模型、专业组合边界、图元解析规则和具体后端选型。若直接以某个绘图软件的文档作为系统模型，会产生以下问题：

- 图元、坐标和页面成为第二事实源，连接语义可能与 SDL 漂移；
- 平面图元、原理图符号和渲染器内部对象混为一谈；
- 专业规则通过继承或渲染器回调隐式叠加，字段所有权和优先级不清；
- 缺少型号图元时静默替换图形，造成“看起来像”但端口不完整的交付物；
- 自动排版覆盖人工位置与样式，或者人工在导出文件中的修改无法追溯；
- 布局未完成时无法区分物理空间位置与纯图面坐标。

原理图是多专业共享的交付能力，但系统展开、图元、介质表达、标签和排版约束各有专业规则。首个切片需要支持 HVAC 冷站，同时保持通用绘图内核不依赖 HVAC。本 ADR 决定功能边界、组合架构和技术选型，不表示实现或冷站验证已经完成。

## 决策

### 原理图是 SDL 的可追溯投影

原理图的唯一权威语义来源是选定模型快照中的 Netlist、Layout 及显式注记资产。`DiagramDocument` 是生成后的绘图交换模型，不是新的权威系统模型；SVG 和 draw.io 是交付表示，也不是事实源。

首个 `hvac:system-diagram` target 的推导管线为：

```text
SDL 模型快照
  → HVAC DisciplineProjection
  → DiagramDocument
  → SymbolCatalog 图元解析
  → LayoutEngine 排版与路由（合并显式人工 overlay）
  → DiagramRenderer 输出 SVG 与非压缩 draw.io
  → 语义检查、版面检查和构建证据
```

排版属于 ADR-0013 的主推导管线，不使用不可见的 post hook 修改权威产物。首个实现建议产物为：

| 产物                | 内容                                           |
| ------------------- | ---------------------------------------------- |
| `system.json`       | 版本化 `DiagramDocument`、解析后图面及来源映射 |
| `system.svg`        | 确定性矢量图，用于预览、审阅和后续发布         |
| `system.drawio`     | 非压缩 XML，用于人工审阅和受控编辑             |
| `system-check.json` | 语义、图元、版面、降级和人工 overlay 检查结果  |

第一版支持节点、端口、连线、标签、分组、页面、跨页引用、稳定语义引用、排版约束和来源映射。视图契约必须声明系统展开边界、筛选、分组、分页、必需标注及跨页规则；筛选不得被误认为完整系统拓扑。

第一版明确不承诺：

- CAD 级精确定位、施工图深化或物理管线综合；
- 完整在线原理图编辑器；
- 任意 draw.io 文件的无损往返或语义自动反向识别；
- 从像素、文本或 XML 几何猜测系统语义；
- 自动排版必然满足工程审美，人工视觉审核仍是交付门禁。

### 通用绘图模型与专业投影分离

`DiagramDocument` 至少包含以下对象：

| 对象             | 必需语义                                                   |
| ---------------- | ---------------------------------------------------------- |
| Document         | schema 版本、target、profile、view、模型快照及视图状态     |
| Page             | 稳定页面身份、顺序、标题、图幅和分页约束                   |
| Node             | 稳定图面身份、`semantic_ref`、图元请求、端口和标签         |
| Edge             | 稳定图面身份、`semantic_ref`、源／目标端口、Net 引用和标签 |
| Group            | 有明确来源的组成或视图分组，不凭空推断空间归属             |
| Annotation       | 文本或标记、所有者、来源、状态和可选语义引用               |
| LayoutConstraint | 顺序、对齐、分组、固定位置、间距和路由偏好                 |
| SourceMap        | 图面对象到 SDL 对象、注记或 overlay 条目的可追溯映射       |

节点、边、端口和页面使用稳定图面 ID，并与 SDL `semantic_ref` 分开。图面 ID 不绑定坐标、数组顺序、SVG 元素 ID 或 draw.io 内部 ID。同一语义对象因分页或可读性需要重复出现时，各图面 occurrence 必须指向共同语义身份，并指定规范 occurrence 和跨页引用，不能被统计为多个设备或多条连接。

物理 `Layout`／`Placement` 与图面排版严格区分。ELK 产生的坐标只表示图面位置，不得回写 SDL 物理坐标；缺少物理 Placement 也不阻塞纯连接视图。

专业通过显式契约组合，不引入 `DiagramBase`、专业多继承或覆盖通用渲染器：

| 契约                   | 职责                                                   |
| ---------------------- | ------------------------------------------------------ |
| `DisciplineProjection` | 从专业模型产生通用绘图对象、语义引用和视图约束         |
| `SymbolCatalog`        | 按图元请求返回版本化、端口兼容的图元及解析证据         |
| `LayoutEngine`         | 消费绘图对象、约束和人工 overlay，返回坐标、尺寸与路由 |
| `DiagramRenderer`      | 将已解析图面序列化为指定格式，不解释系统拓扑           |

契约以数据输入和显式返回值组合。通用规则与专业规则只叠加，不通过方法解析顺序、注册顺序或“后注册者获胜”解决冲突。

### 原理图符号采用有限且可审计的回退链

原理图使用 schematic symbol，与设备在平面或三维场景中的几何表达分离。设备族或设备型号可以提供原理图符号，但不能用平面图元暗含不存在的端口、介质或连接。

`SymbolDefinition` 至少声明：稳定符号 ID、版本、内容摘要、适用视图、包围盒、端口位置、标签锚点、旋转／镜像规则及渲染表达。`SymbolRequest` 至少携带：实例语义引用、设备族、可选型号、型号配置摘要、视图、端口契约和专业标签需求。`SymbolResolution` 返回实际图元、回退层级及证据。

解析顺序固定为：

```text
实例／target 显式指定
  → 型号 + 配置
  → 设备族
  → 专业通用符号
  → 按端口契约生成的中性几何
  → unresolved
```

解析遵守以下不变量：

1. 型号只引用版本化图元，不在型号记录中内嵌大段 SVG 或 draw.io XML。
2. 型号级解析键必须包含规范化配置摘要；配置改变端口时，不得只按型号 ID 复用图元。
3. 每一级候选图元都必须覆盖当前实例的必需端口。端口不兼容时继续回退，不得继续使用“更接近”但语义不完整的族图元。
4. 中性几何由端口契约生成，只能降低视觉保真度，不得减少或虚构端口和连接。
5. 端口契约本身不足时才进入 `unresolved`；按 target profile 报告 `indeterminate` 或 `fail`，不得静默通过。
6. 每次解析记录请求图元、实际图元、回退原因、目录版本、`presentation_exact` 和 `semantic_ports_complete`。任何回退都进入检查和构建证据。

`presentation_exact` 只描述图元是否满足指定精确表达，不表示设备选型、空间位置或专业设计已经确认；`semantic_ports_complete` 独立表示端口表达是否完整。

### ELK 负责图面排版，渲染器负责格式输出

选择 Eclipse ELK 作为首选自动排版与连线路由引擎。首个实现采用 `elkjs` 适配器：Python 推导管线通过版本化 JSON 输入／输出调用本地 Node.js worker，不依赖网络服务。ELK 消费 nodes、ports、edges、层级分组和布局选项，只返回图面位置、尺寸和路由；texsys 保留语义、图元解析、检查和最终渲染职责。

ELK 的算法选项由 target、view 和专业排版规则显式给出。输入对象使用稳定顺序，Node.js、`elkjs`、布局选项、符号目录、字体及字体度量全部进入依赖锁和证据。具体版本在实施 spike 时锁定，本 ADR 不声称已经验证其版本、质量或跨平台确定性。

SVG 由通用渲染器确定性写出，固定数字精度、对象顺序和字体策略。draw.io 导出使用非压缩 XML，图元使用 `UserObject` 自定义属性保留稳定图面 ID、`semantic_ref`、来源和回退信息；这些属性用于追溯，不授权把 draw.io 当作权威模型。

人工 overlay 是显式、版本化源资产，优先于自动布局，至少包含目标视图、稳定图面对象引用、允许的位置／尺寸／样式字段、来源和修订信息。合并规则为：

- overlay 只覆盖白名单排版字段，不得修改源／目标端口、连接、介质、设备身份或语义标签；
- 自动布局只补充未被 overlay 固定的字段，重跑不得覆盖有效人工排版；
- 引用消失、视图不兼容、字段越界或约束冲突必须产生诊断，不得静默丢弃；
- 专业事实必须回到 SDL；专业注记和现场确认进入具有所有者、来源与状态的显式注记契约，不得只存在 draw.io 中；
- 重新生成不得覆盖人工事实或专业注记，冲突必须进入检查证据。

第一版只导出 draw.io，不回读。未来若增加回读，也只接受白名单排版字段和显式注记变更，生成带冲突报告的 overlay／注记变更候选；语义编辑必须形成明确模型变更命令，不能从几何或 XML 差异猜测。

### Layout 不完整时生成显式降级的连接视图

缺少 Placement 时允许生成 `connectivity-only` 视图，图面坐标全部由排版引擎或人工 overlay 提供。该视图：

- 保留已有设备身份、端口、连接、介质、流向和关键参数标注；
- 不生成没有依据的位置、分区、标高、距离、方向或安装关系标注；
- 不把自动排版形成的上下左右关系解释为物理空间关系；
- 在 `system.json`、图面状态和检查证据中显式标记降级及缺失输入；
- 只有显式要求物理空间完整性的 target／profile 才因此无法闭环。

已有部分 Layout 时，只能使用确有依据的空间信息。视图按非空间分类分组时，必须标明分组来源，不得伪装成物理区域。

### 包和依赖边界

建议按以下包实施：

| 包                    | 职责                                                                           |
| --------------------- | ------------------------------------------------------------------------------ |
| `texsys-diagram`      | 专业无关的绘图模型、组合契约、图元解析、overlay 合并、检查及 SVG／draw.io 导出 |
| `texsys-diagram-elk`  | ELK JSON 适配、Node.js worker 协议和排版证据                                   |
| `texsys-hvac-diagram` | HVAC 系统投影、图元目录、介质／标签规则和排版约束                              |

依赖方向单向：`texsys-hvac-diagram` 可以依赖通用绘图包和 HVAC 模型包，`texsys-diagram-elk` 依赖通用绘图契约，`texsys-diagram` 不得导入 HVAC 或 ELK 实现。首个 target 为 `hvac:system-diagram`；在独立闭环需求出现前，不公开更多中间 target。

## 备选方案

### 直接以 draw.io 作为系统模型和自动排版内核

不采用。draw.io 适合编辑、交换和人工审阅，`UserObject` 也能携带追溯属性，但文档几何与自由编辑不能替代 SDL 的端口、Net 和 Layout 语义，也不能提供本项目所需的受约束确定性推导。draw.io 保留为导出格式和后续受控编辑入口。

### 使用 Graphviz 作为首选工程图排版器

不作为首选。Graphviz 可作为简单拓扑图的备选后端，但首个工程切片需要显式端口、层级分组、固定人工位置、跨页表达和更细的工程路由约束，因此选择 ELK。后端适配契约允许以后通过新 ADR 增加或替换实现。

### 自研完整自动排版与路由引擎

不采用。首个切片需要验证的是模型到图纸的闭环，而不是重复实现通用图布局算法。只自研专业约束、交换模型、检查和渲染适配。

### 第一版引入 Sprotty、React Flow 或完整在线编辑器

延后。这些技术可以服务未来的交互式模型编辑，但不是 SVG／draw.io 交付闭环的前提，过早引入会扩大状态同步、事实源和界面验证范围。

### 为 HVAC 复制一套绘图实现或建立专业基类层次

不采用。复制会导致检查、overlay 和格式语义漂移；基类和多继承会隐藏规则覆盖顺序。通用机制与专业规则必须通过版本化契约组合。

## 后果

### 收益

- SDL 保持唯一系统事实源，原理图、SVG 和 draw.io 可以从同一投影确定性生成。
- 通用绘图能力可被其他专业复用，HVAC 规则无需进入通用包。
- 图元缺失不会破坏端口和连接语义，视觉降级及原因全部可追溯。
- 物理布局和图面布局解耦，早期仅连接设计也能交付明确标注的中间视图。
- 自动排版与人工排版所有权明确，重跑不会静默覆盖专业判断。
- ELK、SVG 和 draw.io 各自承担清晰职责，后端可独立验证和替换。

### 代价与风险

- 新增通用绘图 schema、三类包和 Node.js 工具链，需要维护协议及版本兼容。
- 图元目录需要端口契约、配置摘要、版本和字体度量管理，不能依赖临时图片文件。
- ELK 输出质量、确定性和人工 overlay 合并仍需真实冷站 spike 验证。
- draw.io 中的追溯属性不能保证用户不修改语义；第一版通过禁止回读控制该风险。
- 自动检查不能替代工程图可读性审核，首版仍保留人工视觉门禁。
- 通用契约只覆盖当前切片，不声称已经解决所有专业的复杂图纸和交互编辑需求。

## 验证与复审

### 冷站 spike 门禁

使用包含冷机、泵、冷却塔以及冷冻水、冷却水两条环路的真实小系统，完成 SDL 到 SVG 和非压缩 draw.io 的双输出，并进行人工视觉审核。spike 至少验证：

1. 范围内必需设备、端口、Net 和连接按视图契约完整表达，无丢失、虚构或错误连接；重复 occurrence 和跨页引用可追溯。
2. 每条边绑定有效源／目标端口，图元端口完整；坐标和路由数值有限，无契约禁止的遮挡、重叠、越界或跨页歧义。
3. 型号配置变化能选择正确图元；族图元端口不兼容时继续回退，所有回退均可追溯，禁止静默回退。
4. 无 Placement 时可生成显式 `connectivity-only` 视图；保留拓扑标注且不伪造空间标注。
5. 人工 overlay 优先于自动布局，失效引用和冲突有诊断，重新生成不覆盖有效人工排版或专业注记。
6. 相同输入、overlay、字体、图元目录、布局选项和后端版本重复构建得到确定性产物；相关版本均进入证据。
7. SVG 和 draw.io 均可打开，draw.io 导出对象保留稳定语义引用；导出成功不代替 target 闭环。

拓扑检查必须直接检查 `DiagramDocument` 与模型投影，不用像素比较代替；版面自动检查与人工视觉审核分别记录。若 ELK 适配、输出质量或确定性门禁失败，以新 ADR 复审后端，不通过隐藏后处理或放宽语义检查掩盖失败。

### 复审条件

- 引入 draw.io 回读、在线编辑器或图面语义编辑时；
- 增加第二个真实专业，现有投影或图元契约需要规则覆盖时；
- 引入新的排版后端、跨平台确定性要求或复杂图纸模板时；
- 中间绘图产物需要成为独立公开 target 时。
