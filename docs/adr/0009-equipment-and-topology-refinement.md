# ADR-0009：建立设备与拓扑的分层映射规则

- 状态：已接受
- 日期：2026-11-05
- 取代：无
- 被取代：无

## 背景

ADR-0008 将阶段 2 定义为架构与拓扑、阶段 3 定义为行为与容量、阶段 4 定义为实例与布局。实际工程中，阶段 2 通常使用设备族探讨方案；阶段 3 可能已经引用概念设备或具体厂家型号的性能数据；阶段 4 则必须形成能够映射到采购、制造、施工、生产和资产对象的实例级模型。

这会产生两个容易混淆的问题：

1. 使用具体型号数据是否意味着已经选定该型号；
2. 简化拓扑展开为详细模型后，如何判断二者仍然一致。

阶段不能由数据具体程度单独决定。数据具体程度、设计承诺程度和模型保真度是三个独立维度，必须分别记录。

## 决策

### 设备表达层级

| 层级               | 含义                                                                                 | 典型使用阶段                             |
| ------------------ | ------------------------------------------------------------------------------------ | ---------------------------------------- |
| **设备族**         | 按功能、原理、接口和能力包络划分的抽象类别，不绑定厂家型号                           | 阶段 2，也可用于阶段 3 的初步分析        |
| **概念设备**       | 为方案评价构造的代表性设备及其性能模型，不声称对应现实产品                           | 阶段 3                                   |
| **产品型号**       | 具有明确厂家、型号、资料版本和适用工况的外部产品定义                                 | 阶段 3 的候选评价，阶段 4 的选型绑定     |
| **Component 定义** | SDL 中可复用的类型定义，可以承载设备族、概念设备或产品型号语义，但必须声明其来源角色 | 阶段 3—4                                 |
| **Instance**       | 项目中的具体对象，具有稳定身份、参数绑定和所属层级                                   | 阶段 4                                   |
| **外部实现对象**   | 采购项、制造项、BOM 项、生产对象、资产标签或实际建成对象                             | 阶段 4 的计划映射，阶段 5—6 的实施与实证 |

Component 与 Instance 的现有区别保持不变。本 ADR 不要求通过继承体系表达所有设备族和型号关系，也不要求把所有厂家资料复制进 SDL。

### 引用不等于选定

阶段 3 可以引用具体产品型号的容量、效率、曲线、工作范围和其他性能指标，作为简化行为与容量模型的输入。此类引用必须记录资料来源、版本、适用工况和确认状态，但默认只形成**候选参照**，不自动形成采购或实例承诺。

设备承诺按以下顺序显式形成：

1. **候选引用**：用于方案比较，不表示选型批准；
2. **批准选型**：由授权主体确认采用某概念设备或产品型号；
3. **实例绑定**：项目 Instance 引用已批准的 Component 定义并绑定参数；
4. **外部实现**：通过采购、制造、施工、资产或竣工记录证明其现实映射。

项目可以在阶段 3 提前批准选型，但必须记录该承诺，不能利用阶段编号掩盖决定已经发生。更换型号或关键参数时，必须识别受影响的容量、布局、实施和性能证据。

### 抽象拓扑的合法简化

阶段 2 的简化拓扑是有意抽象，不是任意省略。允许：

- 将多个未来设备聚合为一个功能角色；
- 用一条抽象连接表示未来的实际连接路径；
- 暂缓表示阀门、传感器、支撑、标准件和其他从属对象；
- 用能力包络和抽象接口代替具体产品参数。

简化必须保留主要功能、关键接口、容量与能量路径、冗余、隔离和故障语义，并登记后续展开义务。不得通过省略关键设备或接口制造虚假的可行性、容量裕量或低实施成本。

### 两条显式映射

#### 设备映射

```text
设备族
  → 概念设备／候选产品型号
  → 批准的 Component 定义
  → 项目 Instance
  → 外部实现对象
```

设备映射允许一对多、多对一和受控的多对多。一个抽象泵组可以展开为多台并联泵，一个物理成套设备也可以实现多个抽象功能角色。映射关系必须说明原因，不能为了维持表面一对一而复制对象或隐藏组合关系。

#### 拓扑映射

```text
抽象功能角色
  → 一个或多个具体 Instance

抽象连接
  → 实例端口、Connection、Net 及必要中转对象构成的实现路径
```

拓扑一致不等于图形相同。阶段 4 的每个范围内抽象角色必须有实现对象或经批准的开放项，每条抽象连接必须有实例级实现路径。因依赖闭合新增的辅助对象可以没有独立的阶段 2 角色，但必须记录其产生依据和所属关系。

### 阶段 4 的映射闭合规则

阶段 4 的阶段门至少检查：

1. 范围内抽象角色和连接均已映射，或具有明确责任人、状态和后续条件；
2. 不存在未经依据产生的新主要功能或关键接口；
3. 阶段 3 已承诺的容量、冗余和接口未被静默削弱；发生变化时重新评价并批准；
4. Instance 的身份稳定，Component 引用、参数、单位、Port 和坐标参考明确；
5. 产品资料具有来源、版本和适用条件，未知、假设和未确认值未被伪装成已知值；
6. 采购、制造、BOM、生产或资产映射引用同一实例身份，不建立互相独立的事实副本；
7. 映射差异、豁免和未闭合项均进入证据清单。

映射记录至少应能表达源对象、目标对象、关系类型、版本、状态、依据和未解决项。具体字段与语法由后续交换模式定义，本 ADR 不预设当前 JSON 子集已经支持这些关系。

### 设计一致性与现实一致性分离

阶段 4 形成的是**实例级权威设计模型**。其目标是保持从架构、候选设备到项目实例及计划生产对象的可追踪一致性，而不是天然声称与现场实际系统一致。

与实际建成系统的一致性必须由采购、制造、施工、调试、竣工映射、资产登记、试验或运行证据进一步确认。现场差异可以回流设计并触发复审，但不得静默回写设计意图，也不得把详细模型或仿真成功直接报告为现实一致性。

## 备选方案

### 所有层级强制一对一

不采用。设备组、成套设备和多功能部件天然存在一对多和多对一关系，强制一对一会扭曲模型。

### 阶段 3 禁止使用具体产品数据

不采用。真实产品数据可以尽早排除不可行方案。需要控制的是选型承诺和数据适用条件，而不是数据的具体程度。

### 以图形相似度判断拓扑一致性

不采用。抽象连接和详细路径在视觉上可以不同，一致性应由功能、接口、身份和实现路径证明。

### 将阶段 4 直接定义为真实系统镜像

不采用。设计期详细模型只能声明计划实现和映射能力，现实一致性需要外部证据。

## 后果

### 收益

- 可以使用真实产品数据提高早期分析质量，同时保留方案选择和采购决策空间。
- 抽象拓扑与实例级 Netlist 可以合法演化，并通过映射审查而不是图形比较判断一致性。
- 采购、制造、生产和资产对象能够追溯到同一项目实例，降低多份清单漂移。
- 设计一致性、实施状态和现实一致性不再互相冒充。

### 代价与风险

- 多对多映射、版本追溯和开放项管理会增加模型与审查成本。
- 厂家资料可能具有许可、保密和版本限制，外部引用必须遵守其使用边界。
- 映射记录本身也可能失真，需要测试、抽查和外部证据校准。
- 当前 JSON 交换子集尚未实现完整映射语法，本 ADR 不表示工具已经能够自动证明全部闭合规则。

## 验证与复审

- 使用暖通示例覆盖设备族、候选型号、批准定义和项目实例的完整链条。
- 分别验证一对多设备组、多对一成套设备、抽象连接展开和辅助对象依赖闭合。
- 未映射角色、无依据新增关键接口、容量静默降低和身份漂移必须产生失败或无法判断，而不是通过。
- 设计模型与外部实现对象不一致时，必须保留差异并触发复审，不得自动覆盖。
- 实现映射交换模式、采购／BOM 适配器或竣工回流时，复审字段、所有权和自动检查范围。
