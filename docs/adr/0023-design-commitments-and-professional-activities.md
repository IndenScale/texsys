# ADR-0023：区分设计承诺层级与专业活动并统一容量归属

- 状态：已接受
- 日期：2026-11-11
- 修订：ADR-0008 的第三层命名、容量归属与阶段解释；其余证据分级原则保留
- 补充：ADR-0012、ADR-0018

## 背景

[ADR-0008](0008-six-stage-sysda-model.md) 以六个主要承诺层级组织系统设计，将第三层称为“行为与容量”。当前[统一语言](../ul/glossary.md#专业设计流程)采用七项专业活动，并已区分总容量确定、容量分配和原理设计。

两种表达描述不同维度。把它们当成相互竞争的阶段编号，会把验证推迟到最后，或使原理设计同时承担容量需求、设备配置和行为计算，难以解释发现缺口后应改变什么。

工程开发 POC 需要从一次变更追踪到受影响的承诺和证据，允许设计者修改、探索和撤回决定。

## 决策

### 六层描述承诺，七项描述工作

保留六个承诺层级作为理解交付内容和回退原因的分类。第三层采用“原理设计”，表达行为承诺；容量需求和分配分别归属前两层。七项专业活动用于组织工程师开展的工作，不与承诺层级逐项对应。

| 承诺层级     | 承诺内容                                             | 主要相关专业活动                                  |
| ------------ | ---------------------------------------------------- | ------------------------------------------------- |
| 1 需求与规格 | 规定工况下的总容量、可靠性、空间等要求和验收准则     | 01 需求定义；06 工程验证核对准则                  |
| 2 架构与拓扑 | 技术路线、功能网络、容量分配、冗余配置与接口         | 02 架构设计；07 跨专业设计协调                    |
| 3 原理设计   | 既定配置下的工作原理、控制、瞬态、故障和降级行为     | 03 原理设计；06 工程验证                          |
| 4 实例与布局 | 型号与实例、参数绑定、具体连接、位置、路由及空间约束 | 04 部件选型；05 物理设计；07 跨专业设计协调       |
| 5 实现与交付 | 制造、安装、施工、测试及交付过程的资源和实施约束     | 04 部件选型；05 物理设计；06 工程验证及相应 DfX   |
| 6 性能与韧性 | 详细性能、扰动与恢复的适用证据及剩余不确定性         | 06 工程验证；必要的原理、选型、物理设计和协调活动 |

工程验证、跨专业协调和 DfX 贯穿设计；发布是固定设计和证据的交付里程碑。层级分类不要求先完成一层才能开始下一层，也不设整个项目唯一的当前阶段。

### 容量与反馈的职责

需求定义确定规定工况下的稳态 0D 总容量；架构设计分配容量、选择设备台数与能力规格。原理设计使用这些配置研究系统行为，发现瞬态、寄生或故障引起的能力缺口后，形成有依据的新需求，反馈需求或架构层重新决定。

原理分析可以计算容量是否足够，但不能静默改变容量需求或配置承诺。部件选型提供真实能力范围，物理设计提供几何提取值，二者都可能触发重新判断。

### 设计状态独立演化

沿用 [ADR-0018](0018-deliverable-semantics-and-baseline-gates.md)：逻辑信息与空间信息独立演化；BOM、系统图、原理图和布置图是模型投影。粗布置可以先于行为完成，承诺可显式撤回或修改。

基线接受针对明确的交付范围检查条件与证据。历史接受保留，但输入、规则或依赖变化后需要重新核对适用性。一个专业或一条模型链的概念接受，不自动成为整个项目的正式工程批准。

### 工程操作与数据兼容

本决策澄清设计活动和承诺归属，不自动迁移已有 `current_stage`、target ID 或历史证据。专业阶段仍按 [ADR-0012](0012-multidisciplinary-interface-contracts.md)独立记录；既有记录通过明确映射解释。

输入状态、执行状态、回归符合性、工程判定、证据适用性和人工接受分别表达。有限模型、实物试验、现场验证等证据仍受各自适用范围约束，高保真不自动意味着高可信。

## 取舍与后果

- 保留六层分类和七项活动的已有使用基础，避免增加第三套编号流程；实现需要支持多对多映射。
- 容量决定有清楚归属，但工程师仍需要判断新发现的缺口是需求变化、配置不足还是模型条件有误。
- 工作副本可以不完整，接受入口需要解释具体缺项和影响，不能仅显示一个总进度或“阶段完成”。
- 当前 POC 先证明有限模型链的变更、重算和证据闭环；通用需求／约束／决定模型仍按[工程 POC 台账](../engineering-poc.md)推进。

## 验证与复审

1. 同一实例的路由变化能够追踪到几何输入、行为结论和相关接受记录。
2. 行为分析暴露容量缺口时，变更记录明确是修改架构配置还是修正原假设。
3. 缺少行为或空间信息时仍能表达合法中间状态，并在接受对应承诺时指出缺口。
4. 验证活动可以在多个承诺层级运行；界面和命令不得强制按六层或七项活动顺序推进。
